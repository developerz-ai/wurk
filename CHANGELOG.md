## [1.7.1] - 2026-08-10

A correctness release about what Wurk says about itself. An audit of `lib/` against the Sidekiq revision the parity suite pins measured 0.47% overlapping code (66 matching 6-line windows out of 13,996); two files carried enough of it to be worth re-expressing, and they are now Wurk's own. The docs that described all of this were wrong in both directions — overstating Sidekiq's licence permissiveness while also claiming copying that had not happened — and are corrected. No Redis key, command sequence, job-JSON field, or public API changed: a 1.7.0 worker and a 1.7.1 worker can drain the same queue.

### Fixed

- **Provenance claims in the docs were wrong, in both directions.** `docs/clean-room.md` stated that the `test/parity/` files were "lifted from Sidekiq's own MIT-licensed test suite". Two errors in one sentence: Sidekiq is **LGPL-3.0** (`sidekiq.gemspec`, `LICENSE.txt`), not MIT, and the parity tests are not copies of upstream test files — they are independently written oracles using Wurk's own helpers and class names. `test/parity/README.md` compounded it by instructing contributors to "copy it verbatim from upstream Sidekiq". Both are corrected: the page is now [`docs/compatibility.md`](docs/compatibility.md), it states Sidekiq's actual licence, and the parity README describes writing oracles from the documented behaviour rather than copying LGPL files into an MIT repository.
- **"Clean-room" was the wrong term and is no longer used.** Clean-room is a term of art requiring separated specification and implementation teams with records kept to prove independent creation. Wurk was not built that way. It is an **independent reimplementation** of a published interface, which is what the docs now say (README, `docs/migrate-from-sidekiq.md`, site footer). The *Google v. Oracle* rationale is kept but scoped honestly: it covers declaring code, it was a fair-use ruling on its facts rather than a categorical rule, and it says nothing about trademark.
- **Two enumerator helpers were re-expressed as Wurk's own code.** `IterableJob::CsvEnumerator#rows`/`#batches` and `IterableJob::ActiveRecordEnumerator#relations_size` had converged on upstream Sidekiq's exact phrasing — the latter down to a shared trailing comment. Both are rewritten from the behaviour they owe: `CsvEnumerator` now shares one cursor-skipping pass between rows and batches instead of duplicating a lazy chain, and `relations_size` uses `fdiv(...).ceil`. Enumerator element shapes, `#size` values (including the `nil`-path and record-count-not-batch-count quirks a drop-in app already sees), and cursor-resume semantics are unchanged.

### Changed

- **The README now shows the benchmark numbers instead of linking to them.** Two theme-aware SVGs built from the published measurements: throughput as a dot plot with min–max whiskers against a 1.00× parity line (the spread is the story — a bar chart hides it), and boot-to-first-job as a paired bar. Both lead with "Wurk is not faster than stock Sidekiq today" rather than cropping to the flattering rows. Method and per-invocation records stay in [`docs/benchmarks.md`](docs/benchmarks.md).
- **The feature matrix is now a coverage table.** OSS / Pro / Ent / **Wurk** columns with checkmarks, mapped tier by tier off `docs/target/sidekiq-{pro,ent}.md`, plus a second table for the surface Sidekiq has no equivalent for at any tier. It replaces a prose "area → tier" table that never actually showed what a migration covers.
- **The Kubernetes section covers the whole operational surface** — probes, StatsD/DogStatsD export, historical metrics, OpenTelemetry, the `/v1` API, and cluster-wide queue caps — and says plainly that there is **no native Prometheus `/metrics` endpoint**; StatsD or the `/v1` API is the path into a Prometheus/Grafana stack.
- **The GitHub repository description no longer claims speed.** v1.7.0 removed "meaningfully faster" from every file, but the repo description is set in GitHub's settings rather than in the tree, so no grep or PR review reached it and it kept making the claim publicly. It now reads "fork-based multi-core swarm" — a true differentiator instead of an unsupported one.
- Comments that described Wurk's code as matching Sidekiq's source "byte-for-byte" now describe the behaviour and the contract that fixes it (`redis_client_adapter.rb`, `iterable_job/active_record_enumerator.rb`, `lua.rb`). Where the interface genuinely leaves no room for a different expression — `Configuration::DEFAULTS` key names, the JSON log field names, `RedisClientAdapter::BaseError`, the `ServerMiddleware` accessors — `docs/compatibility.md` now names those fragments and says why they are fixed, rather than leaving the resemblance unexplained.

## [1.7.0] - 2026-08-10

A maintenance release with three unrelated threads: the Ruby that runs between `conn.call(...)` and the socket got cheaper, CI stopped running the same suite four times, and the docs stopped writing about Sidekiq at length. No Redis key, command sequence, job-JSON field, or public API changed — a 1.6.0 worker and a 1.7.0 worker can drain the same queue.

### Added

- **`Wurk::CommandBuilder` — an allocation-free fast path for Redis command normalization.** redis-client's default builder splices Hash arguments with a `flat_map` and stringifies the result with a `map!`: two array allocations and two per-element type dispatches for a command whose arguments are already Strings, which is what all three commands per job are (`LMOVE`, `LREM`, `DEL`) and both on the enqueue path (`SADD`, `LPUSH`). The fast path short-circuits that case; a Hash to splice, a Symbol or number to stringify, keyword arguments, or an empty command all fall straight through to redis-client's own builder, so the semantics keep exactly one implementation. Installed as the pool default, and a host-supplied `command_builder:` still wins. Measured **~2.1µs → ~0.48µs per command** (`bin/rake bench:command_builder`, now in the regression gate); the frame disappears from the fetch+execute CPU profile entirely, where it was 4.4%, and the `flat_map` it drove falls from 4.3% to 2.1%.
- **`Wurk::PidCache` — `Process.pid` memoized across forks.** glibc dropped its `getpid` cache in 2.25, so `Process.pid` is a real syscall (~640ns measured), and the hot path called it twice per job: `Component.tid` and `Fetcher::Reliable#queue_keys`, both of which read it *only* to notice a fork. The memo refreshes in the child half of every fork through the `Process._fork` hook (prepended, so it composes with other gems' hooks), which is the only event that can change the answer. The frame was 1.0% of the fetch+execute CPU profile and is now absent from it.
- **`bin/profile` — sample a hot path against a real Redis.** `bin/profile` (fetch+execute), `bin/profile enqueue`, `--alloc` for allocation counts, `--dump` to keep the raw StackProf dump. `rake bench` says *that* something regressed; this says *where*. stackprof is a development-group dependency, never a gemspec one.
- **`bin/check` — the pre-PR gate in one command.** `bin/check fast` (rubocop + unit), `bin/check` (+ full suite + parity), `bin/check full` (+ ecosystem). Refuses to start without a local Redis and says how to get one; prints a per-stage wall clock so the slow stage is obvious.

### Changed

- **`require "wurk"` is ~35% cheaper: ~290ms → ~186ms.** Three subtrees pulled heavy stdlib into every boot for code most processes never reach. `Wurk::CLI` required `optparse`, `yaml` and `erb` at load (~45ms) for a command-line parser only `exe/wurk` runs; `Wurk::Profiler` required `tempfile` (which drags in `tmpdir`, ~19ms) for a path that needs vernier loaded *and* profiling switched on for a job; and `Wurk::Web::Extension` required `erb` and `cgi` (~40ms) although nothing reaches them until a host has registered a Web extension and a request arrives. Each now requires inside the one method that uses it — `require` is idempotent, so every call after the first is a `$LOADED_FEATURES` lookup. What is left is dominated by `openssl`, which redis-client's own config pulls in and Wurk cannot avoid. This is boot time for every worker, every fork in a swarm, and every Rails app that loads the gem.
- **Docs no longer name individuals, and say much less about Sidekiq.** The README's *On Sidekiq* note, *Why Wurk exists*, `docs/clean-room.md`, `docs/migrate-from-sidekiq.md`, the site and `llms.txt` all carried multi-paragraph appreciations of Sidekiq's history and its maintainers by name. That is now one line of substance in each place: Sidekiq is human-maintained and funds that through its paid tiers, Wurk is AI-maintained, and that is what lets the same surface be free software. The independence/non-affiliation disclaimer and the trademark attribution stay — they are the parts that carry legal weight. `llms.txt` instructs agents not to name individual maintainers of either project.
- **The README states what Wurk is for.** It is in production at developerz.ai and partner deployments — millions of jobs an hour across many servers — and it is aimed at large fleets in particular: Kubernetes `/live`+`/ready` probes from a config line, a bearer-scoped HTTP API for non-Ruby producers, OpenTelemetry propagation, cluster-wide per-queue concurrency caps, and monitoring built into the dashboard you already mount rather than a separate stack.
- **CI runs one Ruby suite per PR instead of four.** It was a three-leg version matrix (3.3/8.0, 3.4/7.2, 4.0/8.0) plus a separate `coverage` job running the identical suite a second time under SimpleCov — four executions to answer two questions, on Rails lines that were no longer the newest. Now: one job, newest Ruby (4.0) × newest Rails (8.1), with `COVERAGE=1` on the same invocation so the test gate and the line+branch coverage gate share a run. The gemspec's `>= 3.2` floor is held by rubocop's `TargetRubyVersion: 3.2`, which rejects syntax and APIs newer than it. Parity and bench moved to the same pins so they share one gem cache. The ecosystem, pages and release jobs deliberately stay a Ruby behind: ecosystem's subject is third-party gems at pinned upstream SHAs, and Ruby 4.0 dropped `benchmark` from the default gems that sidekiq-cron's own suite requires; pages and release make no compatibility statement, so a newer interpreter there is risk without upside.
- **The parallel test-worker count is now documented rather than incidental.** It stays at 4, and `test_helper` says why: the suite reads like a pure fan-out of independent classes, but its integration layer boots real swarms (4 children × 5 threads each) and carries real socket timeouts, so one worker per core oversubscribes and fails on wall clock instead of on assertions — measured at ~20% wall clock for a red build on a 12-core box. `NCPU` is the knob for a machine with headroom; `NCPU=1` chases ordering flakes.
- **`JobLogger` reads `logged_job_attributes` once**, in its constructor, instead of walking the capsule's delegating `config[]` per job for a list that is fixed the moment the configuration freezes (1.4% → 1.0% of the profile). Altogether the three changes above take about 6% out of a CPU path where roughly a quarter is socket syscalls, and move `bench/memory.rb`'s allocation gate — which is deterministic, unlike the throughput benches — from 6.49 to 6.76 jobs per 1,000 allocations (~4% fewer allocations per job).
- **Redis service containers in CI probe every 2s instead of every 5s**, and `rubocop` runs `--parallel` behind a result cache.

### Fixed

- **`CsrfSameOriginTest` no longer flakes on a stolen fixture.** It seeded the global `retry`/`schedule` zsets at `Time.now` — immediately due — and those keys are un-namespaced by wire-compat, so any poller or `/wurk/api/<set>/all/<cmd>` drain running in a sibling suite on the same worker's Redis DB could promote or delete the entry between `setup` and the request, which then 404'd. Fixtures are now scored an hour out (invisible to every poller, and the route key is just `<score>|<jid>`), and the class opts out of `parallelize_me!` for the same reason `ApiMutationsTest` already does — non-parallel tests run serially in the runner thread, so the two suites can no longer interleave.
- **The 10k-job global-concurrency drain test scales its budget with the worker count.** Its 120s wall clock was a hang detector calibrated at 4 parallel workers; at a higher worker count the same 4-child swarm gets a smaller share of the machine and the test failed on throughput rather than on the leak it actually asserts.

## [1.6.0] - 2026-08-09

A "beyond Sidekiq" release: eight Wurk-only extras, none of them Sidekiq parity. Every one is additive-only — off by default, zero Redis round trips on the hot path unless opted in, no existing Redis key, sorted-set score, or job-JSON field changed. Full plan and per-slice sign-off: [`docs/plans/2026/08/07/101-beyond-sidekiq/overview.md`](docs/plans/2026/08/07/101-beyond-sidekiq/overview.md).

### Added

- **Job status, progress & results (`Wurk::Status`).** Opt-in `sidekiq_options track: true` persists a `status:<jid>` Hash — lifecycle state, coalesced in-job progress writes (`Worker#status`, one write per 5s window), and the terminal return value (8 KB cap, withheld rather than stored plaintext when the job is also `encrypt: true`). Zero-cost when unset — one Hash lookup, no extra command. No `Sidekiq::Status` alias: the `sidekiq-status` gem owns that constant name upstream (see `lib/wurk/compat.rb`). [`docs/job-status.md`](docs/job-status.md). (#402)
- **HTTP producer + observe API (`Wurk::API`).** A bearer-token-scoped `/v1` JSON API — enqueue, bulk-enqueue, delete, and inspect queues/jobs/swarm topology — RFC-9457 `problem+json` errors, `Idempotency-Key` support, optional read-only mode and per-token rate limiting. Lazily required, so an app that never calls `config.api_token` pays no boot-time cost. Ships standalone (`mount Wurk::API`), engine-nested (`<mount>/api/v1`), or via `wurk api`; a thin Python reference client lives in `clients/python/`. [`docs/api-http.md`](docs/api-http.md). (#403, #406, #407)
- **OpenTelemetry tracing (`Wurk::Telemetry`).** Opt-in `config.telemetry = true` (requires the optional `opentelemetry-api` gem, never a runtime dependency). Client middleware injects W3C `traceparent`/`tracestate` as top-level job-JSON strings on push; server middleware opens one span per attempt in the OTel messaging vocabulary, parenting to the enqueue span within 60s and falling back to a span *link* beyond that so a job stuck for hours doesn't stretch one trace across it. Retries reuse the original `traceparent`. `Job::Interrupted`/`JobRetry::Handled` (incl. `Skip`, `Limiter::Rescheduled`) record as non-errors; everything else records as an error span. (#403)
- **Flows — DAGs on batches (`Wurk::Flow`).** Each flow node is one job wrapped in its own `Wurk::Batch`; `depends_on:` names build a dependency graph (cycle/`MAX_NODES`(1,000)/`MAX_DEPTH`(50)/`MAX_WIDTH`(100) validated before any Redis write, atomically created in one Lua script), and `pipe:` splices an upstream node's `Wurk::Status` result into a downstream node's args without a JSON round trip. `Flow.abandon(fid)` is a kill switch. No `Sidekiq::Flow` upstream surface exists — checked against the pinned parity SHA and RubyGems before aliasing `Sidekiq::Flow = Wurk::Flow`. [`docs/flows.md`](docs/flows.md). (#411)
- **Per-job timeouts & deadlines (`timeout:` / `deadline:`).** `timeout:` bounds a single attempt (raises `Wurk::Job::TimedOut`, retried on the class's own policy); `deadline:` bounds the job as a whole from enqueue (raises `Wurk::Job::DeadlineExceeded`, books `stat:expired`/`jobs.expired`, never retried). Both are enforced by `Wurk::Watchdog`, one lazily-spawned monotonic timer thread per capsule — measured at 3.0µs/bounded job versus 4.5µs for stdlib `Timeout` and 27.4µs for thread-per-job. Unbounded classes cost one Hash lookup. [`docs/retries.md`](docs/retries.md). (#404)
- **Debounce, throttle-to-slot & collapse (`collapse:`).** `sidekiq_options collapse: { policy: :debounce, wait:, max_wait: }` coalesces a burst of pushes into one job — the *last* payload, fired once the burst goes quiet, in one atomic Lua script. `collapse: { policy: :throttle, slot: }` admits the *first* push per fixed, epoch-aligned time slot and drops the rest. Named `collapse:` rather than the plan's original `unique:` after checking that `sidekiq-unique-jobs` already maps `unique:` to its own `lock:` option — reusing it would silently break a host's existing declaration. Conflicts with `unique_for:`/`unique_until:` are rejected at both class-definition time and push time; `push_bulk` rejects a batch outright rather than deciding per item (measured: 1,000 jobs = 2 commands/1 round trip rejected, vs 6,000 commands/1,000 round trips per-item). [`docs/unique-jobs.md`](docs/unique-jobs.md). (#405)
- **Global per-queue concurrency caps (`config.global_concurrency`).** `config.global_concurrency = { "critical" => 20 }` caps in-flight jobs for a queue across the whole cluster — a Lua-scripted slot claim folded into the existing fetch pipeline (no added round trip when capped), released on every exit path including a `SIGKILL`'d slot holder (TTL-recovered), refreshed on the existing heartbeat pipeline. A capped-and-full queue is skipped locally with a short backoff so other queues stay fair; unconfigured stays at the same 3.00 commands/job baseline. Distinct from the per-key `Wurk::Limiter`s — see [`docs/rate-limiting.md`](docs/rate-limiting.md) for which to reach for. (#410)
- **Dashboard theme, locale & timezone.** Light/dark/system theme (`config.web.default_theme`, live `prefers-color-scheme` listener, pre-paint stamp to avoid a flash of the wrong theme); a server-negotiated `#wurk-root[data-locale]` hint mirroring the SPA's exact/language-only/default match algorithm across 8 locales; a filterable ~400-zone timezone picker (`wurk.tz` override) applied to every relative and absolute timestamp in the SPA, with a shared live-tick timer so relative labels stay current with no per-cell polling.

### Changed

- **Docs now credit Sidekiq rather than position against it.** The README, [`docs/migrate-from-sidekiq.md`](docs/migrate-from-sidekiq.md), [`docs/clean-room.md`](docs/clean-room.md), the site and `llms.txt` framed Sidekiq's tiers mainly as something to be freed from ("what you'd otherwise pay for", "no per-seat math"). That undersold a decade of work the whole ecosystem is built on: Sidekiq's API is the one Wurk implements, and the Pro/Enterprise model is what funded keeping it stable and documented long enough to be worth reimplementing. A new **Why Wurk exists** section (README, and an `#why` section on the site) states the actual difference — Wurk is maintained AI-first, which is what makes a free Pro + Enterprise surface, mechanically-verified parity on every push, and this feature cadence sustainable — and says plainly that Sidekiq Pro/Enterprise remain the better choice for teams who need a commercial support contract. `llms.txt` carries the same instruction so agents summarising Wurk don't manufacture a rivalry. No behavior or API change.
- **Job JSON gains new top-level, additive-only fields — never sent unless the corresponding feature is opted into.** `traceparent`/`tracestate` (telemetry), a `status:<jid>` side-record keyed off `track: true` (no job-JSON field, a separate Redis key), `timeout`/`deadline`/`deadline_at` (per-job bounds — `deadline:` is the input option and is kept verbatim; `deadline_at` is the absolute cutoff derived from it once, at push), `collapse` (debounce/throttle policy). Precedent for additive top-level keys: `job_util.rb`'s existing `TRANSIENT_ATTRIBUTES`, plus `sidekiq-cron`/`sidekiq-unique-jobs` both adding their own. None of these are read by, or break, an unmodified Sidekiq worker.

### Fixed

- **An interrupted `IterableJob` run no longer books as a failure.** `Metrics::History#call` and `Metrics::Statsd#call` now rescue `Wurk::Job::Interrupted` and re-raise it unmodified, so the exception propagates up through them to `InterruptHandler` without flipping the `success` flag. Both metrics middlewares now book an interrupted run as `jobs.success` + duration, never `jobs.failure` — matching upstream's own `Sidekiq::Metrics::ExecutionTracker` treatment of `JobRetry::Skip`. A resumed run that later completes books a second success and duration on top of the first, intentionally, as the job re-enters the middleware chain. Chain order verified in regression tests. (#394)

## [1.5.0] - 2026-08-07

A performance release, and the first one to publish honest numbers against stock Sidekiq rather than a slogan. The fetch path went from ~4 Redis round trips per job to ~1, the swarm parent now warms the Lua cache once for the whole fleet instead of once per child, and a resource-lifecycle audit closed the leaks and shutdown races that only show up in a process that has been up for a week. Three of the round-trip wins are behavior-visible and are documented as intentional divergences — read *Changed* before deploying. The "Faster." claim is gone from the gem summary, the dashboard and every translation: wurk is currently **0.87×–1.02×** stock Sidekiq depending on workload, at parity on CPU- and I/O-bound jobs and still behind on framework overhead and boot. The numbers, the method, and the command to reproduce them are in [`docs/benchmarks.md`](docs/benchmarks.md).

### Added

- **`leader_initial_wait` — defer the first leader-election CAS.** A booting process used to spend some of its opening round trips on a `SET NX EX` campaign for the cluster leader lock. `Leader` now waits `leader_initial_wait` before its first attempt, so the job path gets those round trips instead; a shutdown arriving during the delay wakes on the same condition variable rather than waiting the delay out. Documented in [`docs/configuration.md`](docs/configuration.md). (#391)

### Changed

- **Fetch, ack and metrics batched down to ~1 Redis round trip per job (from ~4).** Three behavior-visible trades, all wire-compat (no key/field/score-format change), signed off in [`docs/plans/2026/08/06/101-faster-than-sidekiq/00-semantics-signoff.md`](docs/plans/2026/08/06/101-faster-than-sidekiq/00-semantics-signoff.md) and recorded as intentional divergences in [`docs/idea/parity-divergences.md`](docs/idea/parity-divergences.md):
  - **Paused-queue visibility across processes is now bounded at 2 seconds instead of immediate.** `Fetcher::Reliable` caches the paused-queue set behind a 2s monotonic-clock TTL instead of an `SMEMBERS` on every fetch pass. A `pause!`/`unpause!` issued from *within* the fetching process itself still takes effect on that process's next fetch pass; cross-process propagation is bounded by the TTL. `Wurk::Queue#paused?` and the dashboard/API still read Redis directly and are unaffected. In practice this does not move the fleet's worst case: an idle worker parked in `BLMOVE` already couldn't notice a pause faster than its poll interval (default 2s).
  - **Dashboard per-minute/per-class job counters now lag by up to 5 seconds, and a hard kill (`SIGKILL`, OOM, box loss) can drop up to 5 seconds of unflushed counters for that process.** `Metrics::History` accumulates counts in memory, keyed by the minute bucket computed at record time, and flushes on a ≤5s timer (plus on every graceful stop) instead of writing on every job. Bucket attribution is unaffected — only visibility lag, never misattribution. This was already a best-effort write path (a Redis failure here never affects a job's outcome); Sidekiq itself batches these on a 10s heartbeat and wurk's cadence is tighter.
  - **The redelivery window after a hard process death widens from "immediately after the job finishes" to "the next fetch, or the next flush point, whichever comes first."** A completed job's `LREM` off the private list is now held by the fetcher and piggybacked onto the next `BLMOVE`/`LMOVE` pipeline instead of sent as its own round trip. Wurk is still at-least-once and a job is never lost; what widens is the same duplicate-execution window `docs/reliability.md` already documents, not a new failure class, and it's unreachable by a graceful shutdown (acks flush before `bulk_requeue`, before blocking, before `terminate`). Idempotent job handlers remain the required mitigation, unchanged.
  - Net effect measured in [`08-measurements.md`](docs/plans/2026/08/06/101-faster-than-sidekiq/08-measurements.md): commands/job 10 → 3 (one round trip), `fetch+execute` 1.41k → 2.53k i/s.
- **The swarm parent loads Lua once for the whole fleet.** `Swarm#boot` runs `script_load_all` on the supervisor pool between `close_parent_sockets` and the fork loop, so the children inherit a warm `EVALSHA` cache instead of each re-uploading all 25 scripts; `ChildBoot#validate_redis!` keeps only its `PING`. Measured server-side (`INFO commandstats`) across five 8-child boots: **1000 → 125 `SCRIPT` calls** (200/boot → 25/boot). A preload that never warmed, or a cache wiped by a Redis restart between the load and the fork, still self-heals on first use. In the same pass `Configuration#prepare_for_fork!` materializes every capsule's middleware chains and freezes `@options` in the parent, so children inherit warmed copy-on-write pages rather than each rebuilding them. (#391)
- **Each child starts fetching before it starts polling.** `Launcher#run` brings up the managers, heartbeat, reaper and boot-reclaim sweep first and the periodic loops second, so a freshly forked child is taking jobs while its background timers are still coming up. (#391)
- **The gem summary no longer claims "Faster."** `spec.summary` on RubyGems, the `Wurk` top-level docstring, the dashboard tagline in all eight locales, and the CodeRabbit review invariants all asserted wurk was faster than stock Sidekiq. It is not — see [`docs/benchmarks.md`](docs/benchmarks.md). The claim may not go back until the published numbers support it (CLAUDE.md pillar 3). No behavior change; this is the metadata and UI catching up with the measurements that landed in 1.4.0's wake.

### Fixed

- **`Stats::History` read a different day than `Launcher` wrote.** The writer keys `stat:processed:<day>` / `stat:failed:<day>` / `stat:expired:<day>` off `Time.now.utc`, but the reader defaulted its window to `Date.today` — the *local* civil date. On any host not running UTC, that asks for a day the writer never wrote for whatever slice of each day the offset spans: the newest bucket comes back `0` and the whole window is shifted by one. A dashboard on a UTC−5 host showed an empty or stale "today" for the last five hours of every day. The default is now `Time.now.utc.to_date`, matching the writer exactly; an explicitly-passed `start_date` is untouched.
- **Dashboard assets now send `Cache-Control`.** `Wurk::Engine::AssetMount` is inserted at index 0 of the *host application's* middleware stack, so `Rack::ETag` and `Rack::ConditionalGet` never saw its responses and the precompiled bundle was re-fetched in full on every page load. Fingerprinted assets are now cached immutably for a year; everything else revalidates. (#384)
- **Resource-lifecycle audit — leaks, shutdown races, and a supervisor that reaped too much.** Every fix carries its own regression test, mutation-checked against the pre-fix code (#392):
  - `Swarm#reap_children` / `hard_kill_stragglers` waited on *any* child pid, so in an embedded or standalone boot the supervisor could reap — and hard-kill — subprocesses the host application had spawned for its own reasons. Both now wait only on pids the swarm tracks.
  - Every shutdown join is now bounded (reaper, leader, the launcher's stoppers, embedded TERM handling), and `Launcher#stop` releases its Redis pools on every path rather than only when embedded.
  - `Processor::WORK_STATE` had a publish window where a job was running but not yet visible to the dashboard's Busy pane; it is now an RAII `track` frame. `Configuration#lookup` no longer raises `FrozenError` against a frozen `@directory`.
  - Four retention leaks: `PoisonPill.on_poison` now dedups by callable identity and returns a removable registration, `Heartbeat` stopped leaking a file descriptor per beat (`File.foreach` → `File.open`), `Web::Config#rack_app` re-keys its memo on `[inner, middlewares]` instead of serving a stale app, and `Client::Buffered#reset!` no longer orphans its drainer thread.
  - The SSE concurrency guard is self-healing: slots are scoped to thread identity instead of counted, so a hard-reaped stream thread no longer permanently 503s `/api/stream`.
- **A stale comment on `JobSet#schedule` described the opposite of the code.** It claimed `ZADD` with `NX` "so re-scheduling the same payload doesn't reset its score"; the call has no `NX` and never did. The behavior is correct and matches `Sidekiq::JobSet#schedule` — the last schedule call wins — so the comment was corrected rather than the code.

### Known issues

- `Wurk::Metrics::History` books a cooperatively-interrupted `IterableJob` as a failure, inflating the dashboard's failure rate for apps that interrupt iterable jobs across restarts. The chain ordering, the blast radius and the parity question that has to be settled first are in [#394](https://github.com/developerz-ai/wurk/issues/394). Rate-limited reschedules are *not* affected — the limiter middleware sits outside the metrics middleware and never yields to it.

## [1.4.0] - 2026-08-02

A five-agent leak, logic and performance audit of the whole gem, landed over eleven pull requests. There is one new keyword argument here and no new features: the rest is the class of bug that only surfaces in a process that has been up for a week, a swarm that has recycled a child, a container that restarted into a fresh PID namespace, or a Redis that blipped mid-write — leaked threads, sockets and file descriptors, keys that grow without bound, retries that silently replayed a write, and a handful of races that lost or duplicated work. Every fix carries a regression test confirmed to fail without it. Read [Upgrading](#upgrading) before deploying: one public method was renamed, the default Redis retry policy narrowed, a Redis key shape gained a segment, and poison-pill kills now reach your error reporter.

### Added

- **`idempotent:` — an explicit apply-safety claim on every Redis accessor.** `pool.with(idempotent: true) { … }` tells `RedisPool` that re-running the block after a command may already have landed server-side is harmless, which buys it back the full connection backoff the new default policy withholds (see *Changed*). The keyword is threaded through every wrapper an application or extension actually touches — `Wurk.redis`, `Wurk::Middleware.redis`, `Component#redis`, `Configuration#redis`, `Capsule#redis`, `Wurk::Limiter.redis`, `Wurk::Cron.redis` — so a custom middleware or dashboard extension doing a pure read opts back in with one keyword rather than hand-rolling its own retry. Claim it only for reads, or for writes whose repeat is a no-op (an owner-CAS script, a `SET` of a constant, an `LMOVE` the reaper would reclaim anyway); claiming it for an `INCR` or an `LPUSH` re-introduces exactly the duplicates the split exists to prevent. Wurk's own genuinely-idempotent hot paths — the fetcher's `SMEMBERS`/`LMOVE`/`BLMOVE`, the reaper's reads, the Data API and dashboard reads, queue pause/unpause, the heartbeat's identity-hash write, `RedisPool#info` — are opted in for you. (#353)

### Changed

- **Redis retries are now decided by apply-safety, not by error class alone.** `RedisPool#with` used to retry *any* `ConnectionError` — including `ReadTimeoutError` and `WriteTimeoutError` — with exponential backoff, on the reasoning that at-least-once tolerates a duplicate. It does not: the block is arbitrary Ruby, so a replay re-issues *every* command in it, and a read timeout means the command may already have applied server-side. Only errors that provably never reached a server still replay by default — `RedisClient::CannotConnectError` and `FailoverError`, plus the `READONLY`/`NOREPLICAS`/`UNBLOCKED` failover path, which is a rejection rather than an outcome. Read/write timeouts and a bare `ConnectionError` now raise. On top of that, the pool watches the connection's round-trip odometer and refuses to replay a non-idempotent block that has already completed one round trip — redis-client re-dials mid-block, so a `CannotConnect` can surface on the *second* pipeline of a block whose first one already landed, and no per-command proof covers the commands ahead of it. Blocks that are genuinely safe to re-run pass `idempotent: true` (see *Added*). Every retry, refused replay and final give-up still reports through `Wurk::Configuration#on_redis_error`. (#353)
- **`Wurk::Client::Buffered::Overflow#payload` → `#payloads`** (Array). The exception now carries *every* undelivered payload rather than the single one that tripped the cap. Callers doing `rescue Overflow => e; Outbox.create!(payload: e.payload)` become `e.payloads.each { … }`. See [`docs/reliability.md`](docs/reliability.md#the-durability-caveat).
- **A poison-pill kill now notifies death handlers.** When the reliable fetcher's recovery counter crosses `RECOVERY_THRESHOLD` the payload goes to the dead set — but it went there with `notify_failure: false`, so nothing downstream ever heard about it. `Wurk::Batch::DeathHandler` *is* a death handler, which meant a poison-killed job never decremented its batch's pending count: `:death` never fired, `:complete` never fired, and the batch hung forever with no error recorded anywhere. The kill now runs the death-handler chain with a `Wurk::Middleware::PoisonPill::Poisoned` exception whose message names the class and the recovery count (`"MyJob was recovered 3 times without completing"`), which is also what `:death` batch callbacks and any error reporter will see. Every other terminal path in Wurk — retry exhaustion, `:discard`, the limiter's reschedule cap — already notified; a poison kill is the same kind of event. Sidekiq Pro's spec is silent on the question, so the choice is recorded in [`docs/idea/parity-divergences.md`](docs/idea/parity-divergences.md).
- **`Batch#on` deduplicates identical callbacks and caps a batch at 1,000 of them.** Re-registering the same `[event, target, options]` triple is now a no-op instead of appending a second copy, and past `Wurk::Batch::CALLBACKS_MAX` (1,000) the registration is refused with a logged warning. The shape this exists for is common and quietly quadratic: reopening a batch by bid inside every job and calling `on(:success, …)` there re-encodes the whole `callbacks` array on every append (O(N²) Lua work on the way in) and then enqueues N identical callback jobs when the event fires. The dedup is applied on both sides of the first flush — in-memory before it, in `BATCH_APPEND_CALLBACK` after — and normalises both sides through cjson, so `{a: 1}` and `{'a' => 1}` are recognised as the same callback. (#357)
- **Concurrent limiter — `held` and `overages` now mean what the documentation says.** `held` was never written on acquire at all; it is now bumped inside `limiter_concurrent_acquire.lua`, atomic with the `ZADD` (so a process dying mid-acquire can't undercount) and costing no extra round trip. `overages` counted acquires that exhausted `wait_timeout` — but that path raises `OverLimit` and is already counted per job in `overrated`. It now counts what the release script's contract says it counts: a holder that outran `lock_timeout` and found its slot already reclaimed when it released. Dashboards and alerts reading either counter will see different numbers after upgrading. (#355)

### Fixed

- **Swarm — a forked child could `SIGKILL` its own siblings on exit.** The child inherits the swarm object *and* `rails_boot`'s `at_exit { swarm.shutdown }`, so `ChildBoot`'s `exit` ran a full parent-style drain from inside a child, where `@children` holds its *siblings*: TERM to all of them, a 30-second stall waiting on pids it can never reap, then SIGKILL. One child exiting for any reason took the fleet with it. `boot` now records `@owner_pid` and `shutdown` / `supervise` / `safe_kill` no-op off it, and the `at_exit` registers before `boot` and only sets a flag the supervise thread observes. (#344)
- **Swarm — `can't add a new key into hash during iteration` under respawn.** `@children` and the restart state machine were touched from the supervise thread, the signal thread and the exit path at once. Both now live behind one reentrant `Monitor` (they are mutually recursive, so separate locks deadlock), readers walk snapshots, and `hard_kill_stragglers` kills and clears atomically. (#344)
- **Swarm — `USR2` reopened the children's logs but not the parent's.** The parent relayed the signal and never reopened its own descriptors, so after a logrotate the master kept writing into the deleted inode. It now reopens and relays. In the same pass, `shutdown` closes both ends of the self-pipe, `emit_signal` / `read_pending_signal` tolerate the pipe vanishing mid-drain, and `CLI#run` closes its pipe on every exit path and always drains the swarm. (#344)
- **Swarm — the parent reopened Redis sockets it had just closed before forking.** `heartbeat_seen?` ran on the capsule's main pool, so at concurrency ≥ 10 it re-opened, in the parent, exactly the sockets `close_parent_sockets` had shut — and every later respawn or restart fork inherited them. It now uses a dedicated single-connection pool that is disconnected immediately before every `Process.fork`, restoring the documented boot ordering. (#344)
- **Launcher — the shutdown tail leaked whatever the first failing step left behind.** `Launcher#stop` ran its teardown as a straight sequence, so one raising release step skipped every step after it. The whole tail now runs under `ensure` with each release independently guarded; the `TimerLoop`-driven components (`History`, `Metrics::Rollup`, `Metrics::QueueRollup`, `Scheduled::Poller`, `Cron::Poller`) join their thread with a bounded timeout and clear it on terminate instead of abandoning it; the heartbeat's stop handshake uses a `Mutex` + `ConditionVariable` rather than a `Thread#wakeup` that is lost if the target is not yet asleep; and `stop` joins the boot-time reclaim thread (bounded) before the rest of teardown touches Redis. (#346)
- **Launcher — a partial embedded boot left orphan threads running forever.** If `Wurk::Embedded#run` raised part-way, the host application was told Wurk never started while whatever the launcher *had* got up kept fetching, beating and campaigning for the leader lock, unowned, for the life of the process. A failed boot now rolls itself back (reporting a rollback failure separately so the caller still sees the original error), and `at_exit` registers before `run`. Embedded `#stop` also disconnects the configuration's Redis pools, so a stop-then-run cycle in a long-lived host no longer doubles the socket set on each pass; this is scoped to embedded mode, where the host outlives Wurk. (#346)
- **Launcher — a failed Processor replacement killed the host application's main thread.** When `Manager` could not spawn a replacement for a dead Processor (a `ThreadError` at the OS thread limit, typically) it called `Thread.main.raise`. That unwound straight past `Manager#stop`, so the in-flight `UnitOfWork`s were never `bulk_requeue`d and each one waited out a full reaper interval — and in embedded mode it killed the host's main thread rather than just the worker. The Manager now asks its owner to shut the process down through the normal path: a swarm child or standalone CLI re-delivers TERM to itself so the installed trap drives a real drain, embedded mode stops the launcher in place. `Manager.new(capsule)` keeps its old arity. (#346)
- **Fetcher — all queues paused turned every processor thread into a hot loop.** `Processor#run` drives `process_one` in a bare `until @done` loop with no pause of its own, so any `nil` returned instantly spins. `Fetcher::Reliable#retrieve_work` returned `nil` immediately when `queues_cmd` came back empty — which is what a fully paused (or unconfigured) queue set looks like — costing an `SMEMBERS` on the main pool per pass, as fast as the CPU allows: ~3,000 Redis calls a second per process, measured. It now sleeps a full poll interval on that path, and a short `QUIET_PAUSE` on the quieted short-circuit (`Manager#quiet` terminates the shared fetcher before the processors, so there is a window where every processor sees an instant `nil`). The pause is kept below `Manager::PAUSE_TIME` so it adds no drain latency. (#348)
- **Iterable jobs — an interrupted job resumed *behind* the entire backlog.** `InterruptHandler` re-pushed the job with `LPUSH`, described as "head of queue, so it is fetched next". It is not: the reliable fetcher's `LMOVE` pops from the *right*, so an `LPUSH`'d job goes to the back of the line and a long-running iterable job resuming after a restart waited out every job enqueued before it — including ones enqueued *after* the interrupt. The re-push is now `RPUSH`, which is genuinely next. (#348)
- **Reliable fetch — the reaper mistook a container restart for a live worker (and vice versa).** Private-list keys were `queue:<q>|<host>|<pid>|<idx>`, and the fast liveness check was `Process.kill(0, pid)` for any key whose host matched ours. Under a container restart into a fresh PID namespace, or `hostNetwork` sharing without PID-namespace sharing, that pid means nothing in our namespace: a dead owner's pid can be alive here (its jobs are never reclaimed and sit stranded until something else notices) and a live owner's can be free here (its private list is drained out from under it and its in-flight jobs run twice). The key now carries `Component::PROCESS_NONCE` — `queue:<q>|<host>|<pid>|<nonce>|<idx>` — and `kill(0)` is used only when the nonce is our own; every other incarnation falls through to the namespace-blind heartbeat check (`processes` SET membership), which waits out the 60s TTL exactly as the spec describes. The reaper parses both the new five-part and the legacy four-part key shape, so a rolling upgrade does not strand jobs written by not-yet-upgraded processes; the ambiguity is resolved by trying the wide reading first and taking whichever leaves a real public-queue name behind. Pid reuse within one namespace remains the documented blind spot, matching Sidekiq Pro's `super_fetch`. (#349)
- **`reliable_push!` replayed jobs Redis had already accepted.** A push is several round trips — one pipeline per destination queue, then the batched `BATCH_PUSH` pipeline — but the outage buffer took the whole payload set whenever any of them raised. A `push_bulk` spanning two queues that lost the connection after the first `LPUSH` landed, or any mixed plain + batched push whose batch phase failed, re-buffered payloads that were already enqueued and ran them a second time on the next drain. `Wurk::Client` now records each queue group as its reply comes in and `Buffered` re-buffers only the residual. The group in flight when the socket drops stays at-least-once (a lost reply is indistinguishable from a lost command); everything confirmed before it is not replayed. See [`docs/reliability.md`](docs/reliability.md#client-side-redis-outage-buffering).
- **`reliable_push_overflow = :raise` silently dropped payloads.** `Buffered.enbuffer` raised from *inside* its append loop, so a bulk push that crossed the cap buffered the payloads before the offending one, raised carrying only that one — and left every payload after it neither buffered, nor enqueued, nor referenced anywhere. A 1000-job `perform_bulk` against a nearly-full buffer lost up to 998 jobs with no error naming them. The split is now decided against remaining capacity before anything is appended: the buffer takes what fits and one `Overflow` carries the rest. The same raise also pre-empted the `bid`-carrying re-raise, stranding batched payloads (which never buffer) in a mixed push; they are now folded into the same exception, with `cause` still the connection error.
- **The outage buffer was not fork-safe — every swarm child replayed the parent's buffered jobs.** The buffer, its drainer and both of its mutexes are process-global and were copied wholesale into each child, so a fork taken while jobs were buffered enqueued the lot once per child *plus* once from the parent: `(children + 1) × N` duplicates. Worse, a fork taken from inside either critical section left the child holding a mutex whose owner thread did not survive, and its first `Client#push` (which drains, so it synchronizes, before pushing) blocked forever. `Buffered.reset_after_fork!` now rebuilds the buffer, drainer and mutexes per process, driven from both the `Process._fork` hook and `Swarm::ChildBoot#reconnect_after_fork` (whichever runs first wins; the pid guard makes the other a no-op). The child *drops* its inherited payloads rather than replaying them — the parent still holds the same buffer and replays it on its own next push — and a parent-configured drainer is replaced by an equivalent fresh one so an opted-in child keeps flushing what it buffers itself. In the same pass the drain pool is resolved late through the configuration instead of a pinned pool object, and `emit_enqueued` stopped double-counting buffered pushes as both enqueued and recovered. (#352)
- **Five Redis call sites replayed a write that may already have applied.** These are the concrete losses the retry-policy split above exists to prevent, each confirmed and fixed with fault-injection coverage: `Client#atomic_push` re-pushed a job whose `LPUSH` reply was lost (a duplicate job), `Scheduled#zpopbyscore` re-ran a pop whose reply was lost (a *lost* scheduled job — the members it popped were already gone), `Launcher#write_stats` double-counted processed/failed counters, `Heartbeat#drain_signals` dropped a dashboard-issued TERM/TSTP on the floor, and `PoisonPill#bump_counter` double-incremented a recovery counter and could kill a job one reclaim early. A real-TCP-blip integration test now asserts a seeded `<identity>-signals` entry survives a heartbeat retry exactly once — no drop, no duplicate. (#353)
- **Leader election — releasing the lock could delete somebody else's.** `Leader#release` was `GET` then `DEL`. Between the two, our own key can lapse and a follower can win the election — and the bare `DEL` then deletes *that* process's lock, leaving the cluster leaderless (or, once the ex-leader re-campaigns, doubly led) for up to a renew interval. Double leadership means double cron fires and double metric rollups. The compare and the delete now happen in one server-side step, through the `release_if_owner` script `Wurk::Unique` already shares. (#354)
- **Leader election — two racing `start` calls leaked an unkillable second campaigner.** The nil-check ran inside the mutex but the thread spawn ran outside it, so both callers could pass the check and both spawn; the loser's thread was never recorded in `@thread`, survived `stop`, and went on renewing the cluster lock forever. The spawn now happens inside the lock (the same pattern the Reaper uses). (#354)
- **Periodic — a leader handover could fire the same schedule slot twice.** The leader gate is a cached read, so for a few seconds after a handover two pollers can both believe they lead and both reach the same due loop. Each then read the `lf`/`nf` fire marks, enqueued, and wrote the marks back — a read-modify-write with no arbitration. The marks now advance through a single-Lua compare-and-swap (`cron_claim_fire`) *before* the enqueue, so only the tick still looking at the mark it read owns the slot. The consequence of putting the claim first is that a failed push drops that occurrence rather than risking a duplicate one; the drop is logged with the lid and class. Manual `Cron#fire` deliberately skips the CAS — an operator-requested run contends with no schedule slot. (#354)
- **Window limiter — reading `status` from the dashboard could wipe a live window.** `Window#size` and `#status` computed their cutoff from the *calling host's* clock and then `ZREMRANGEBYSCORE`d against it, on every dashboard GET. A web host running more than one interval ahead of Redis therefore evicted live entries just by rendering the page, and the next callers charged the limit a second time. Both are now genuinely read-only: one `ZCOUNT` + `ZRANGEBYSCORE` in a read-only Lua script deriving the cutoff from Redis's own `TIME`, in a single round trip. Trimming stays exclusive to the acquire script, which still enforces the limit after any skewed read. (#355)
- **Bucket limiter — a waiting job busy-polled every 50 ms instead of sleeping to the boundary.** `secs_to_next` was computed and then discarded inside a `.min` that could never select it, so the wait loop woke twenty times a second for the whole wait. It now sleeps toward the next cardinal boundary (floored at 50 ms, clamped to the remaining deadline). (#355)
- **Batches — sub-keys were created without a TTL and leaked permanently.** Only `b-<bid>` was stamped at first flush; `-jids`, `-failed`, `-died`, `-kids`, `-pkids` and the callback dedup markers were created later, by the Lua push scripts, `link_to_parent` and `record_event`, with no expiry at all. Every one of them outlived its batch forever. Each is now stamped `EXPIRE … NX` at its creation site (NX so a live batch's expiry, and the shorter post-success `linger` window, are left alone), `DeathHandler.restamp_ttls` sweeps the rest on death, and `record_event` re-stamps a hash it resurrects — a child batch's callback firing after the parent's 30-day window had lapsed used to recreate `b-<bid>` with no clock on it at all. `Batch::KEY_SUFFIXES` also gained `complete`/`success`/`death`, the three dedup markers Wurk actually writes, so `Status#delete` now sweeps them instead of leaving them behind. (#356)
- **Batches — the `batches` and `dead-batches` index ZSETs grew for the life of the Redis.** Only `Status#delete` and the death-recovery `ZREM` ever removed a member, and neither runs for a batch simply left to expire, so an index entry outlived by weeks the batch hash it pointed at — and `BatchSet` enumeration got slower forever. `Batch.trim_index` now runs in-pipeline with each `ZADD` (so bounding the index costs no extra round trip) and trims on two axes, in the same shape as the morgue trim: `ZREMRANGEBYSCORE` against the batch expiry window, plus a `ZREMRANGEBYRANK` backstop at `Batch::INDEX_MAX` (1,000,000). A batch that overrode `expires_in` past the default window is still reachable by bid, just no longer enumerated. (#356)
- **Batches — a crash could lose a `:complete` or `:success` callback permanently.** Both fired by claiming their dedup key first and enqueuing the callback second. Nothing ever re-drives that fire — once the acking job's `BATCH_ACK_SUCCESS` has `SREM`'d its jid, that job's retry gets `pending == -1` and returns before `maybe_fire` — so a crash in the window between the claim and the enqueue meant the callback was never enqueued by anyone, ever, and the batch silently stranded. The order is now enqueue-then-mark, with the read-side gate on the marker's existence, so the durable side effect happens before the marker that suppresses it. The accepted direction of the trade is a rare duplicate over a silent loss: callback jobs retry like any other job and are required to be idempotent, and sequential re-invocations (a reclaimed child re-running `propagate_to_parent`, a second `DeathHandler` pass) are still collapsed — the duplicate window is only two genuinely concurrent acks interleaving between each other's check and mark. `fire_death` deliberately keeps claim-before-enqueue: everything that makes a batch *look* dead is already persisted before the guard, so a crash there costs the notification but not the state. (#356)
- **`lmtr-list` grew one permanent member per limiter name.** The spec blesses interpolated limiter names (`stripe-#{user_id}`), which means a limiter is constructed per job and registration sits on the enqueue path — and registration `SADD`'d the name on *every* construction while `lmtr:<name>` expired with the limiter's TTL. The set therefore accumulated a member for every user, order or tenant the application had ever seen, and rendering the dashboard's Limits page got slower forever. Registration is now one Lua round trip (metadata `HSET` + `EXPIRE` + `SADD`, down from three) that only adds to the set when the `HSET` actually created the metadata, and `Web::Enterprise::Limits.list` sweeps names whose metadata has expired — batched at 512 names per pass so a set that leaked for months cannot block every other Redis client for the length of one atomic call, and re-deciding liveness inside the script so a name that re-registers mid-sweep is not hidden until its TTL runs out. (#357)
- **Poison pill — the recovery counter was never cleared, so three unrelated crashes dead-set a healthy job.** `super_fetch:recovered:<jid>` was incremented on every reclaim and only ever decayed on its 72-hour TTL. Nothing reset it on success — and jids do come back: a dashboard or API retry re-pushes the same one, as does any client that supplies its own. Three reclaims caused by three *unrelated* events inside one window — a deploy `SIGKILL`, an OOM kill, a node eviction — therefore moved to the dead set a job that had completed every single time it ran, with `notify_failure: false` so nothing said so. The counter is now retired by the ACK: `Fetcher::Reliable::UnitOfWork#acknowledge` pipelines the `DEL` next to its `LREM`, so an attempt that finished — returned, or raised and booked its retry — starts the next one at zero, and it costs no extra round trip for the jobs (nearly all of them) that were never reclaimed at all. Only an attempt that never acked, because the process died under it, still accumulates, which is precisely the signal the counter is meant to carry. A fetcher plugged in through `config[:fetch_class]` whose unit of work has no `jid` slot simply ACKs as before; its counters age out on the TTL. `Wurk::Middleware::PoisonPill.clear!(jid)` remains available for clearing one by hand.
- **Dashboard — SPA resource leaks on unmount.** An extension page navigated away from mid-fetch left the request in flight and called its setters into a disposed component; it now aborts through an `AbortController` on cleanup. Toast timers were never cleared (a dismissed toast still held a 6-second timer, and a burst of failures grew the list unbounded) — timers are cleared on dismissal and on eviction, and the list is capped at five. `Modal` children are memoized so closing one releases the held subtree instead of retaining it. `prefers-reduced-motion` is now a reactive signal with a listener cleaned up on unmount, rather than a value read once at mount, so toggling the OS setting takes effect without a reload. (#351)

### Upgrading

- **`Wurk::Client::Buffered::Overflow#payload` is gone; use `#payloads`.** It is an Array now, carrying every undelivered payload rather than only the one that tripped the cap. Any `rescue Wurk::Client::Buffered::Overflow => e` handler that reads `e.payload` raises `NoMethodError` after upgrading — grep for it before deploying. Applications that only rescue and log are unaffected apart from the message text, which now names the count. This only applies if you have enabled `reliable_push!` with `reliable_push_overflow = :raise`.
- **Read and write timeouts are no longer retried by default.** A `RedisClient::ReadTimeoutError` or `WriteTimeoutError` that the pool used to absorb with exponential backoff now propagates to your code. In practice the fetch loop, the scheduler and the heartbeat all already rescue and re-loop, so the visible change for most applications is *fewer* duplicate jobs and more `on_redis_error` reports — but a bespoke `Wurk.redis { … }` call site in application code that relied on the pool swallowing a slow-Redis blip will now see the exception. If such a block is genuinely replay-safe (a pure read, an owner-CAS script, a `SET` of a constant), pass `Wurk.redis(idempotent: true) { … }` to restore the old behavior. Do not pass it for `INCR`, `LPUSH`, `ZADD` or anything else whose repeat changes state — that is the duplicate-job bug the split fixes. Connection *failures* (`CannotConnectError`, `FailoverError`) and the `READONLY` failover path are unchanged and still retry.
- **Private-list keys gained a segment: `queue:<q>|<host>|<pid>|<nonce>|<idx>`.** No action is required — the reaper parses both the new five-part shape and the legacy four-part one, precisely so an upgrade does not strand in-flight jobs written by processes that have not restarted yet. Be aware that during a rolling deploy the keyspace holds both shapes at once, and that any external tooling, dashboard or alert that parses these keys positionally needs teaching about the extra segment before it starts mis-reporting owners. Nonce-mismatched owners (which is every pre-upgrade process, from an upgraded process's point of view) are judged by the 60-second heartbeat rather than by `kill(0)`, so reclaim of a crashed old-format worker can take up to a minute longer than it used to during the deploy window. Once every process has restarted, the fast path is back.
- **Poison-pill kills now fire death handlers, so your error reporter will see a new event class.** A job killed after `RECOVERY_THRESHOLD` (3) reclaims previously went to the dead set silently; it now runs the death-handler chain with a `Wurk::Middleware::PoisonPill::Poisoned` exception. Sentry, Honeybadger, a custom `config.death_handlers` entry and any `:death` batch callback will start observing these — that is the point (a stranded batch used to be the alternative), but budget for the alert if your reporter pages on new issue types. Note that the fix above means far fewer jobs reach the threshold in the first place, so the expected volume is low. If you need to suppress the notification for a specific class, filter on `Wurk::Middleware::PoisonPill::Poisoned` in your reporter.
- **Concurrent-limiter counters changed meaning.** `held` is now written on every successful acquire (it previously was not written at all, so any dashboard panel or alert reading it was reading a permanent zero), and `overages` now counts holders that outran `lock_timeout` rather than acquires that exhausted `wait_timeout`. The latter is still counted, per job, in `overrated`. Repoint any alert threshold accordingly.

## [1.3.1] - 2026-07-26

Two drop-in gaps found in one production deploy, both of which only bite the worker process — so the web app looks healthy while nothing gets done. Each fix carries a regression test that fails without it.

### Fixed
- **`mount Wurk::Engine` in `config/routes.rb` crashed `wurk` / `wurkswarm` on boot** — with `uninitialized constant Wurk::Engine`, from the exact routes line the README and the migration guide tell you to write. `lib/wurk.rb` loads the engine behind a `defined?(Rails::Engine)` guard evaluated once at require time; the standalone runners require `wurk` *before* Rails exists, then boot the host app themselves, by which point `wurk` is in `$LOADED_FEATURES` and the app's own `Bundler.require` can't re-evaluate the guard. Web processes were unaffected (there `Bundler.require` runs after railties), so this reached production looking like a worker-only mystery. `Wurk::Engine` now resolves on demand behind the same guard. No `require "wurk/rails"` in routes.rb needed, and a genuinely non-Rails standalone boot still loads zero Rails code — nothing references the constant, so nothing loads.
- **Sidekiq's `network_timeout` (and friends) killed every swarm child on boot** — `config.redis = { url:, driver:, network_timeout: 5, pool_timeout: 5 }`, an ordinary Sidekiq initializer, raised `ArgumentError: unknown keyword: :network_timeout` from redis-client. Sidekiq normalized its `config.redis` hash internally before handing it over; Wurk splatted it straight through. Because the swarm parent closes its connections *before* forking and only the children build pools, the parent stayed up and healthy — Running pod, passing liveness probe, respawn-backoff loop churning forever, zero jobs processed. `Wurk::RedisOptions` now performs Sidekiq's translation for every pool-building path:
  - `network_timeout` / `timeout` fan out to `connect_timeout` / `read_timeout` / `write_timeout`. Not forwarded verbatim: Wurk sets all three explicitly (the split-timeout fix in 1.0.x), and redis-client lets an explicit `read_timeout` beat `timeout`, so passing the umbrella through would have silently dropped the host's value. A host-supplied split timeout still wins over the fan-out.
  - `sentinels:` now builds the pool through `RedisClient.sentinel` — `RedisClient.config` rejects the key outright, so Sentinel deployments hit the same crash. `master_name` maps to `name`; `driver` and `role` are symbolized.
  - `logger`, `cluster_safe` and `pool_name` are accepted and dropped, as Sidekiq did.
  - `namespace` and `nodes` raise naming the key and its replacement, and any other key redis-client would reject raises listing the supported set — read off redis-client's own signatures, so it can't drift from the installed version.
  - `config.redis =` validates on assignment, so a bad hash fails in the process running your initializer instead of inside a forked child nobody is watching.

### Documentation
- `docs/running.md`, `docs/configuration.md` and `docs/migrate-from-sidekiq.md` §3 promised the standalone runners "do fully boot your Rails app" while not loading the engine — true of the engine's *Rails lifecycle* (no initializers, routes or assets), but read as a guarantee that mounting the dashboard was safe, which it wasn't. The claim is now split: the engine doesn't start, but the constant resolves.
- `docs/migrate-from-sidekiq.md` §1 implied `config.redis = {...}` was verbatim-compatible. It gains a per-key table (pass through / translated / rejected) and an upgrade note.

## [1.3.0] - 2026-07-26

Error reporting. `sentry-sidekiq` is the one common add-on that cannot be installed alongside Wurk at all, and the obvious workaround — hanging a reporter off `config.error_handlers` — silently reports nothing from your jobs, because job failures never reach that hook. This release ships the integration Wurk should have had, and documents the trap for anyone rolling their own.

### Added
- **First-class Sentry integration (`Wurk::Sentry`)** — opt-in, and the replacement for `sentry-sidekiq`, which **cannot be installed alongside Wurk**: its gemspec declares `add_dependency "sidekiq"`, so Bundler pulls real Sidekiq back into the app and `require "sidekiq"` resolves to a hybrid of the two. Enable with `require "wurk/sentry"` and `Wurk::Sentry.install!(config)` inside `Wurk.configure_server`.
  - Registers **both** a server middleware and a `config.error_handlers` entry, because either alone is blind. A job failure never reaches `error_handlers` on Wurk — `JobRetry#local` rescues it, books the retry, and raises `Wurk::JobRetry::Handled`, which the processor swallows — so error handlers see only fetch-loop errors, `!shutdown`, invalid JSON, and retry-machinery meta-errors. Any reporter wired only into `error_handlers` (Sentry, Honeybadger, a custom notifier) silently reports nothing from your jobs.
  - **Reports the terminal failure only**, not all 25 retry attempts. `Wurk::Sentry::RetryPolicy` predicts what `JobRetry` is about to conclude, honouring `retry: false`, `retry: <Integer>`, `retry_for:`, and `config[:max_retries]`.
  - **Never sends job `args`** — not in the per-job context, and stripped from any job hash in the error handler's `extra:` (payloads carry PII and `encrypt: true` ciphertext). The raw `jobstr` of an unparseable payload is dropped wholesale.
  - **Filters self-healing transport noise** (`RedisClient::Error`, `ConnectionPool::TimeoutError`) out of the error handler by default — the fetch loop's `rescue → sleep(1)` cycle turns a backend blip into a report per thread per second; one production Dragonfly deployment accumulated ~136,000 events on a single issue while the job pipeline was healthy. Still logged at WARN by the default handler. Opt out with `filter_transport_errors: false`, or replace the list with `filtered_error_classes:`.
  - Transactions are named `Wurk/<JobClass>`, mirroring `sentry-sidekiq`'s `Sidekiq/<JobClass>` so a migrating app's issue history stays legible. Tags: `queue`, `jid`.
  - `sentry-ruby` is **not** a runtime dependency. Every call site is guarded on `defined?(::Sentry) && Sentry.initialized?`, so the code is inert without it. `install!` is idempotent.

### Documentation
- New [`docs/sentry.md`](docs/sentry.md) — why `sentry-sidekiq` is incompatible (and the `ecosystem/sidekiq-shim/` escape hatch), setup, options, the retry and noise-filtering semantics, and a migration section for apps coming off `sentry-sidekiq`.
- `docs/migrate-from-sidekiq.md` gains `sentry-sidekiq` in the third-party gem mappings (§6) and two new known incompatibilities (§7): the gem itself, and the fact that job failures never reach `config.error_handlers` — which breaks *any* error reporter wired only into that hook.

## [1.2.0] - 2026-07-21

Writing the feature documentation against the implementation — rather than against the parity specs — surfaced a cluster of features that looked enabled but quietly did nothing. This release fixes them. Every fix carries a regression test that fails without it.

### Fixed
- **Testing — `require "sidekiq/testing"` did not enable fake mode** — under Sidekiq that require flips testing into `:fake` as a side effect; Wurk's file was a bare `require "wurk"` and the default mode is `:disable`. A migrated suite therefore pushed into **real Redis** while every `MyJob.jobs` assertion came back empty, often without failing. The require now warns once per process (deprecated in Sidekiq 8 in favour of `Sidekiq.testing!`) and enables `:fake`, and it never overrides a mode the suite already chose explicitly.
- **`perform_inline` / `perform_sync` bypassed both middleware chains** — they called `#perform` directly, so unique-job locks were taken at push and never released (leaking until TTL), batch callbacks never fired, and no retry or logging middleware ran. Inline execution now mirrors Sidekiq 8: client chain → JSON round trip → server chain.
- **Unique jobs — ActiveJob dedup was a silent no-op** — an ActiveJob payload's args are `[job.serialize]`, a hash carrying a fresh `job_id` and `enqueued_at` on every push, so the default digest never repeated and nothing was ever deduplicated. ActiveJob-wrapped payloads now narrow the digest to the wrapped `job_class` and its `arguments`. Retry counters are deliberately excluded so a retry re-push still matches its own lock.
- **Unique jobs — `unique_for:` + `encrypt: true` silently depended on initializer order** — both features append to the same client chain, so whether the digest saw plaintext args or a random-IV encryption envelope depended on which ran first; in the envelope case uniqueness never matched again. Pushing a worker that sets both now raises `Wurk::Unique::ConfigurationError`. This is stricter than Sidekiq Enterprise, which documents the incompatibility but lets the silent mis-dedup through.
- **`Wurk::Unique.locked?` ignored `sidekiq_unique_context`** — the probe always digested `[class, queue, args]` while the push path honoured the hook, so it reported "free" for every worker with a custom context. It now routes through the same derivation as the push path.
- **Batches — `callback_class` was inert** — the field was stored and round-tripped but never read, so a class-less `"#method"` callback target silently never fired (a drop-in break for Sidekiq Pro apps using that form). All four documented target forms now resolve. An unresolvable target raises `Wurk::Batch::CallbackJob::UnresolvableTarget` and goes straight to the dead set on the first attempt rather than crash-looping through 25 retries for ~21 days — a `NameError` does not heal with time, so the failure is made visible immediately.
- **Periodic — editing or removing a schedule left the old loop firing forever** — `Cron.unregister` had zero callers despite a comment claiming a Web UI delete action and a config-reload path drove it, so a changed schedule left both the old and new loop running. Registration now prunes loops it supersedes, scoped by class so a process registering a subset never touches another's loops and a client-only process deletes nothing. A `register` line deleted outright still needs manual removal — nothing in the surviving code names that class.
- **Periodic — a dashboard pause was undone by the next deploy** — `register` rewrote the whole loop hash including `paused => "0"`. `paused` is now written with `HSETNX`: code declares the initial value at first registration, and the runtime owns it thereafter.
- **Iterable jobs — no cursor checkpoint on graceful shutdown** — the run loop never consulted the processor's stopping flag, so on TERM/TSTP/USR1 it kept iterating until the deadline, where `Wurk::Shutdown` (an `Interrupt`) escaped the `rescue Interrupted` (a `RuntimeError`). Everything since the last periodic checkpoint was redone on resume. The loop now polls `interrupted?` at each iteration boundary and takes the existing flush-and-re-push path.
- **Iterable jobs — cancelled jobs re-cycled at the head of the queue for three days** — `finalize_interrupted` never deleted the `cancelled` field, so each resume tripped its first check and re-pushed, burning a fetch slot per cycle until the `CANCELLATION_PERIOD` TTL expired. A cancelled job now terminates and deletes its state.
- **Metrics — `top_jobs(hours:)` raised above 8 hours** — the argument was validated against `MAX_HOURS` (72), converted to `hours * 60`, then re-validated against `MAX_MINUTES` (480), so the documented 72-hour ceiling was unreachable. Each argument is now checked against its own cap; 72h is backed by the 3-day minute-bucket retention.
- **Search and the job APIs emitted a null queue** — `SortedEntry` passed the raw JSON string to `JobRecord`, which only derives `@queue` from a pre-parsed Hash, so `#queue` was `nil` for every entry from `each`/`scan`/`fetch`. Dashboard search and the retry/scheduled/dead endpoints all reported `queue: nil`.
- **Dashboard — limiter Reset did nothing for bucket limiters** — the web path deleted a bare `lmtr-b:{name}` while the counter lives at `lmtr-b:{name}:{epoch}`. It now rebuilds the limiter from its persisted metadata and delegates to the type's own `reset`.

### Changed
- **`perform_inline` returns `true`/`nil`** (nil when middleware halts the job) instead of `#perform`'s return value, matching Sidekiq's contract. It now also touches Redis, since it runs the real chains.
- **SIGTSTP (quiet) interrupts an in-flight iterable job** at the next iteration boundary instead of letting it run to completion. Quiet sets the same processor flag as TERM, which is how upstream Sidekiq behaves.

### Documentation
- Fifteen new guides covering features that previously had no user-facing page: authentication, configuration, testing, retries and the dead set, batches, rate limiting, periodic jobs, unique jobs, iterable jobs, reliability, middleware, the Data API, metrics, encryption, and profiling. `deployment.md` gains rolling restarts, `SIDEKIQ_MAXMEM_MB`, Docker, Kubernetes probes, leader election, and sizing.
- **`config.reliable_scheduler!` was wrongly documented as an accepted no-op** in the source comment, the configuration reference, and the migration guide. It is not: the default `scheduled_enq` pops then pushes and has a job-loss window, and the toggle swaps in the atomic promoter. A Sidekiq Pro user following the old migration guide would have dropped a call that was protecting them. Only `super_fetch!` is a genuine no-op.
- Corrected a documented `CONT` signal that has no handler (quiet is one-way), and a README claim that only the first swarm child binds the health port (non-owner children poll and take it over when the owner dies).

### Upgrading
- **ActiveJob unique digests change derivation.** Nothing can become permanently stuck — `unique_for` is mandatory and every lock key carries an `EX` — but during a rolling deploy old and new processes compute different keys for ActiveJob payloads, so dedup is split across two namespaces for the length of the deploy. Locks written by the old code were write-only garbage that never matched anything and simply expire. Apps using the documented `sidekiq_unique_context` workaround on the wrapper are unaffected; the hook still takes precedence.
- If any worker sets both `unique_for:` and `encrypt: true`, enqueuing it now raises. Drop one of the two options.

## [1.1.1] - 2026-07-18

### Fixed
- **Engine — host app boot crash in stock production deploys** — the dashboard asset middleware was inserted with `insert_before(ActionDispatch::Static, …)`, but Rails omits `ActionDispatch::Static` whenever `public_file_server` is disabled (any production deploy behind nginx with `RAILS_SERVE_STATIC_FILES` unset), so `initialize!` raised and the host app would not boot with the gem installed. The middleware now inserts at index 0, which is equivalent (it only intercepts `/wurk-assets/*`) and always valid.
- **Dashboard "Stop" left a standalone process as a zombie** — a TERM queued via the dashboard (`Wurk::Process#stop!`) was dispatched by calling `Launcher#stop` directly on the heartbeat thread: `stop_heartbeat` self-joined (`ThreadError`), skipping heartbeat cleanup and exit hooks, and nothing woke the main thread — the process stopped fetching but never exited, and in a swarm the slot was silently lost. Standalone processes now re-deliver the signal to themselves (`Process.kill`) so the real trap path runs; embedded launchers (which own no traps, and where a self-TERM would kill the host) run quiet/stop on a separate thread with a self-join guard.
- **Swarm — TSTP quiet now sticks across respawn/recycle** — quieting the swarm only relayed TSTP to the children alive at that moment; a crashed or memory-recycled child's replacement booted fetching, violating the one-way global quiet (spec §21.3). The swarm now records the quiet state and forks replacements pre-quieted (a constructor flag, not a racy post-fork signal).
- **Swarm — USR2 to the parent no longer kills the fleet** — the parent had no USR2 trap, so a logrotate config signalling the master pid hit the default disposition and terminated the whole swarm. USR2 is now trapped and relayed to children (log reopen).
- **Swarm — `-t/timeout` finally reaches the supervisor** — the CLI and railtie built the Swarm without `shutdown_timeout`, so the parent SIGKILLed children at the 25s default even when `-t 60` promised them a longer drain, cutting off `bulk_requeue`. The configured timeout is now plumbed through, plus a 5s grace so the children's post-drain tail (requeue + heartbeat cleanup) always fits.
- **Swarm — fork-window signal theft** — a signal delivered to a freshly-forked child before it reset its inherited traps was written into the parent's self-pipe (TERMing one child pid could drain the entire swarm). Children now close the inherited pipe FDs first thing, so the stale trap write no-ops; also frees 2 leaked FDs per child.
- **Client — Redis-outage buffer no longer drops jobs on non-connection errors** — `drain!` popped a buffered job before replaying it, but only connection errors restored it; a recovering Redis answering `OOM`/`LOADING`/`READONLY` permanently discarded one buffered job per drain tick, silently. Every error path now restores the popped payload first.
- **Client — outage-buffer drainer replayed into the wrong Redis** — the drainer captured the origin pool from a nonexistent ivar, always got `nil`, and silently replayed explicit-pool jobs into the default Redis; the one-shot factory guard then blocked any later correct capture. It reads the right ivar now and never installs a nil-pool factory.
- **Scheduler — post-outage promotion no longer stalls Redis** — the reliable scheduler's Lua promote swept every due member in one atomic call; a 100k-job backlog blocked all Redis clients for the whole sweep. Promotion is now batched (500/call, looped until dry).
- **Limiter — `config.redis=` reset the wrong memo** — reassigning the limiter Redis after first use kept returning the stale pool forever.
- **Batch — death of a stale job no longer resurrects expired batch keys TTL-less** — a job dying after its batch's 30-day expiry recreated `b-<bid>*` keys with no TTL (permanent leakage per occurrence). The death handler now re-stamps `EXPIRE … NX` on the batch keys.
- **Cron — Vixie step semantics for single-value bases** — `5/15` in a field parsed as just `[5]`; it now expands to `5-max/15` (5,20,35,50) matching Vixie cron / fugit / Sidekiq Ent.
- **API parity — `set(wait:/wait_until:)` with a past/zero target enqueues immediately** (Sidekiq drops `at` when not in the future) instead of parking in the schedule ZSET; `retry_for` deadline math no longer misreads millisecond timestamps (`Time.at` third-arg unit).
- **Web API hardening** — `?page=` is clamped (array params no longer 500), substr-filtered pages count offsets in match space (no more duplicated/skipped rows across pages) under a 20k-row scan budget, `keys[]` bulk actions cap at 1000, "add all scheduled to queue" snapshots the set so it terminates under concurrent scheduling and never early-enqueues jobs scheduled after the click, `GET /profiles/:key` (which uploads to the public Firefox profiler store) is blocked in read-only mode, and extension render errors no longer leak exception messages to viewers.
- **Web API — fewer Redis round-trips** — the profiles list pipelines `HMGET` of metadata only (previously one `HGETALL` per profile, dragging each multi-MB gzipped blob through Redis per render); queue-job delete uses the single-Lua fast path instead of a paged queue walk.
- **Tests — cron DST assertions were host-timezone-dependent** — `TZInfo#utc_to_local` reinterprets a non-UTC `Time`'s wall clock as UTC; the fold assertions now convert to UTC first (they passed on UTC CI but failed on any non-UTC machine).

## [1.0.3] - 2026-06-16

### Fixed
- **Rails drop-in — engine auto-load** — a host following the README/migration guide (`gem "wurk"`, no `require:`) only loaded the standalone entry point, so the engine/railtie never loaded and `ActiveJob::QueueAdapters::WurkAdapter` was undefined; `config.active_job.queue_adapter = :wurk` then raised `NameError` at boot. `lib/wurk.rb` now mirrors stock Sidekiq and auto-loads `wurk/rails` when Rails is present (idempotent with an explicit `require "wurk/rails"`; the no-Rails/standalone path stays fully Rails-free). (#246, #249)
- **Rails drop-in — build-safe boot** — `Railtie.skip_boot?` didn't cover the build context, so the default Rails Dockerfile's `SECRET_KEY_BASE_DUMMY=1 ./bin/rails assets:precompile` fired `after_initialize`, forked the swarm, and tried to connect to Redis during `docker build` (no Redis there → hang/fail). A new `Railtie.building?` skips boot when `SECRET_KEY_BASE_DUMMY` is set or any rake task is running; `rails server` / `puma` boot via `Rails::Command`, not Rake, so the real server path is unaffected. (#247, #249)

### Changed
- **Dashboard — obsidian redesign** — the dashboard adopts the monochromatic "obsidian" design system (collapsible left rail, range filters, loading states) and the landing page gains per-tier `BorderGlow` on the tier cards. (#248)
- **CI — bench gate de-noised (best-of-N)** — the PR `compare` job intermittently flagged the low-throughput `push_bulk(1000)` bench (~250 i/s) as a regression on pure runner noise: at that iteration count a single noisy base-vs-head pair could clear even the noise-aware ± band (e.g. #249 saw a spurious -18.2% over a ±13.3% band; the re-run passed). The job now runs the bench suite three times per side and `bin/bench-compare` keeps the fastest run per benchmark, so the cross-process tail (GC, runner CPU contention) is damped. Best-of-N is applied symmetrically to base and head, so a real regression — slower on every run — still fails the gate. (#250)

## [1.0.2] - 2026-06-13

### Added
- **Dashboard — per-request read-only** — `/api/meta` now reports a per-request `read_only` flag derived from the registered authorization hook, so a viewer-role user (a hook that permits `GET` but denies mutations) sees the SPA hide destructive actions instead of showing buttons that then 403. The probe asks the hook about `POST` on a canonical mutating route (`/api/retries`) so a path-sensitive hook resolves it the same way the Authorization middleware resolves the real mutation. With no hook registered the flag still reflects global read-only mode. (#244)

### Fixed
- **Config — weighted-queue YAML** — loading a real `sidekiq.yml` with weighted queues in the nested-array form (`queues:` → `- [critical, 2]`, which YAML parses to `["critical", 2]`) crashed at boot with `Integer(): " 2]"` because the queue parser only handled the `"name,weight"` string form. The capsule parser now accepts both the string and nested-array forms; a malformed array entry with extra elements is rejected with an `ArgumentError` rather than silently truncated. (#242)
- **Packaging / standalone** — `require "wurk"` raised `LoadError: cannot load such file -- base64` on Ruby 3.4+ in any non-Rails app. The code requires `base64` and `logger`, which Ruby moved out of the default gems (base64 in 3.4, logger in 3.5); a Rails app pulled them in transitively, masking the gap, but a standalone consumer had neither. Both are now declared runtime dependencies, so the "run without Rails" path works on current Ruby. (#237)
- **Dashboard — Quiet/Stop** — clicking **Quiet** (or **Stop**) on a worker in the Busy page made it silently vanish from the dashboard instead of reporting as quieted. `Launcher#@done` was overloaded: the heartbeat loop ran `until @done`, and `#quiet` set that same flag, so quieting terminated the heartbeat thread — the process never published `quiet=true` and then expired out of the live `processes` set. The quiet ("stop fetching, stay alive") and shutdown ("stop heartbeating") concerns are now split, so a quieted worker keeps beating and stays visible as quiet; `#stop` still drains and removes it. Affected every `wurkswarm` worker. (#236)

## [1.0.1] - 2026-06-11

### Fixed
- **Cron / Periodic** — a cron loop targeting an `ActiveJob` class now enqueues it through the ActiveJob adapter (`perform_later` → `Sidekiq::ActiveJob::Wrapper`) instead of pushing it as a bare Sidekiq worker. Previously the poller did a raw `client.push('class' => "MyActiveJob")`, so the processor would call `MyActiveJob.new.perform` and skip all of ActiveJob (callbacks, argument deserialization, retries). Matches sidekiq-cron behavior. An explicit cron `queue:` still overrides; otherwise the job's own `queue_as` is respected.

First stable release. Wurk is a 100% drop-in replacement for Sidekiq, Sidekiq
Pro, and Sidekiq Enterprise — same Redis schema, same job JSON, same Ruby DSL —
with fork-based parallelism and a precompiled React dashboard, all free in one
gem. This release completes OSS + Pro + Ent feature parity (roadmap #147) and
adds a `require "sidekiq"` compatibility entrypoint so existing apps and
third-party gems swap in with a one-line `gem "sidekiq"` → `gem "wurk"` change.

### Added
- **`require "sidekiq"` drop-in** — a `sidekiq` compatibility shim gem + entrypoint so existing apps and ecosystem gems load Wurk transparently; validated by a real third-party ecosystem suite (sidekiq-cron green on Wurk). (#204)
- **`Sidekiq::Testing`** — `inline!` / `fake!` / `disable!` (global or block-scoped), the in-memory `Sidekiq::Queues` store, and the `Worker`/`Job` test helpers (`.jobs`, `.clear`, `.drain`, `.perform_one`, `.process_job`, `.drain_all`, `.clear_all`) + `Sidekiq::EmptyQueueError`.
- **IterableJob enumerator helpers** — `array_enumerator`, `csv_enumerator` / `csv_batches_enumerator`, and the `active_record_*_enumerator` family, with Sidekiq cursor parity. (#200)
- **Periodic / cron** — public `Sidekiq::CronParser` with `#next` for cron-expression introspection (#201); per-loop execution history in the dashboard (#117).
- **Enterprise historical metrics** — `Sidekiq::History` snapshotter + `config.retain_history` DSL (#123), the `history:metrics` capped Redis stream for migration parity (#125), and per-queue size/latency historical gauges in the dashboard (#124, #126).
- **Swarm lifecycle** — honor `SIDEKIQ_MAXMEM_MB` for memory-based child recycling (#119) and fire an `on(:fork)` lifecycle event in each child after fork (#121).
- **Dashboard** — render third-party Web-extension views/assets natively in the SPA (#187); design follow-ups: human-readable latency, host-grouped Busy page, count-up stats (#217).

### Changed
- **Keyless releases** — the release workflow publishes to RubyGems via **trusted publishing (OIDC)**, no long-lived `GEM_HOST_API_KEY`. - CI standardized on Blacksmith runners with consistent concurrency + job timeouts. (#230)

### Fixed
- **Boot** — enter server mode before the host app loads so `Sidekiq.configure_server` blocks fire in real workers. (#191)
- **Batches (Pro)** — gate a parent batch's `:complete`/`:success` on still-running child batches (#209); fire `:success` correctly after a dead job is manually retried to success, including the ancestor-batch case (#212, #226); persist `Batch#on` callbacks registered after the first `#jobs` flush instead of dropping them (#213).
- **Unique jobs (Ent)** — re-push the job's own jid at schedule/retry promotion instead of losing it to its own lock, and release the lock when a job dies automatically. (#205, #211)
- **Cron (Ent)** — resolve IANA timezone strings via TZInfo instead of mutating process-global `ENV['TZ']`, so concurrent jobs never observe the wrong zone. (#210)
- **Scheduling (Pro)** — compute `expires_in` for a scheduled job from its schedule time, not enqueue time, so a delay longer than `expires_in` no longer makes the job born-expired. (#208)
- **Data API (OSS)** — `Sidekiq::Stats#queues` / `#queue_summaries` sort by size descending to match Sidekiq (#214); fix `SortedEntry#retry` / `#add_to_queue` retry_count handling and fire death handlers on API kill (#206, #207).
- **Dashboard** — redact encrypted job arguments as `"<encrypted>"`. (#118)
- **Test reliability** — give the interrupt-repush integration test's completion clock the same load budget as its boot clock, and 2× that under the coverage CI leg, so it no longer flakes under full-suite CPU saturation. (#216)

## [0.0.1] - 2026-06-01

First public (pre-1.0) release. Wurk is a 100% API-compatible drop-in replacement for Sidekiq + Sidekiq Pro + Sidekiq Enterprise — same Redis key schema, same job JSON, same Ruby DSL — with fork-based real parallelism, the full Pro + Enterprise feature set in one free gem (no license check), and a precompiled React dashboard.

### Runtime
- Fork-based Swarm: parent forks N children with PID supervision, rolling restart (SIGUSR1), graceful drain (SIGTERM/SIGINT) to `shutdown_timeout`, and global pause/resume (SIGTSTP/SIGCONT).
- Reliable fetcher — atomic `BLMOVE` from the main queue to a per-process private list — with orphan reclamation on boot; Processor runs the middleware chain; Manager owns the thread pool, lifecycle, and heartbeat.
- Scheduled-set and retry pollers; EVALSHA-cached Lua on the hot paths; per-fork Redis pool over redis-client; Redis-outage client buffer.
- `reliable_push` opt-in `:raise` overflow policy with a background drainer.
- Cluster leader election with periodic firing consolidated onto the leader.
- StatsD metrics across hot paths; liveness HTTP endpoint for Kubernetes probes; expired-job counter for `expires_in`.

### Batches
- Sidekiq Pro Batch API: `on(:success/:complete/:death)` callbacks, live progress, nested batches, autoflush + linger, nested death cascade, and per-callback rescue.

### Limiters
- Enterprise rate limiters — concurrent, bucket, window, leaky, and points — each exposing a uniform live `#status` (`used`/`limit`/`reset_at`/`available?`); concurrent additionally reports metric counters. Includes a poison-pill brake.

### Periodic
- Cron loops (sidekiq-cron compatible): schedule parsing with timezone/DST handling, leader-gated firing, pause/resume, enqueue-now, and fire history.

### Encryption
- Transparent job-payload encryption with key rotation and graceful failure modes (a decryption failure degrades rather than crashing the worker).

### Dashboard
- Precompiled React + TypeScript SPA mounted under the engine — consumers never run Node. Tabs: queues, retries, scheduled, dead, busy, processes, batches (+ per-batch detail), limiters, periodic, metrics, and search. SSE live updates, read-only mode, pagination, i18n with host-app override, and a dark default theme.

### Compat
- `Sidekiq::*` aliases for every public `Wurk::*` class (`Sidekiq::Worker`, `Sidekiq::Batch`, `Sidekiq::Limiter`, `Sidekiq.configure_server`, …) — the drop-in contract.
- ActiveJob adapter, `IterableJob`, embedded mode, and a standalone `exe/wurk` runner.
- Sidekiq client/server middleware contract; third-party ecosystem suites (sidekiq-cron, sidekiq-unique-jobs, sidekiq-scheduler, sidekiq-status, sidekiq-failures, sidekiq-throttled) pass against Wurk.
