# 1.4.0 — 2026-08-02

A five-agent leak, logic and performance audit of the whole gem, landed over eleven pull requests. There is one new keyword argument here and no new features: the rest is the class of bug that only surfaces in a process that has been up for a week, a swarm that has recycled a child, a container that restarted into a fresh PID namespace, or a Redis that blipped mid-write — leaked threads, sockets and file descriptors, keys that grow without bound, retries that silently replayed a write, and a handful of races that lost or duplicated work. Every fix carries a regression test confirmed to fail without it. Read [Upgrading](#upgrading) before deploying: one public method was renamed, the default Redis retry policy narrowed, a Redis key shape gained a segment, and poison-pill kills now reach your error reporter.

### Added

- **`idempotent:` — an explicit apply-safety claim on every Redis accessor.** `pool.with(idempotent: true) { … }` tells `RedisPool` that re-running the block after a command may already have landed server-side is harmless, which buys it back the full connection backoff the new default policy withholds (see *Changed*). The keyword is threaded through every wrapper an application or extension actually touches — `Wurk.redis`, `Wurk::Middleware.redis`, `Component#redis`, `Configuration#redis`, `Capsule#redis`, `Wurk::Limiter.redis`, `Wurk::Cron.redis` — so a custom middleware or dashboard extension doing a pure read opts back in with one keyword rather than hand-rolling its own retry. Claim it only for reads, or for writes whose repeat is a no-op (an owner-CAS script, a `SET` of a constant, an `LMOVE` the reaper would reclaim anyway); claiming it for an `INCR` or an `LPUSH` re-introduces exactly the duplicates the split exists to prevent. Wurk's own genuinely-idempotent hot paths — the fetcher's `SMEMBERS`/`LMOVE`/`BLMOVE`, the reaper's reads, the Data API and dashboard reads, queue pause/unpause, the heartbeat's identity-hash write, `RedisPool#info` — are opted in for you. (#353)

### Changed

- **Redis retries are now decided by apply-safety, not by error class alone.** `RedisPool#with` used to retry *any* `ConnectionError` — including `ReadTimeoutError` and `WriteTimeoutError` — with exponential backoff, on the reasoning that at-least-once tolerates a duplicate. It does not: the block is arbitrary Ruby, so a replay re-issues *every* command in it, and a read timeout means the command may already have applied server-side. Only errors that provably never reached a server still replay by default — `RedisClient::CannotConnectError` and `FailoverError`, plus the `READONLY`/`NOREPLICAS`/`UNBLOCKED` failover path, which is a rejection rather than an outcome. Read/write timeouts and a bare `ConnectionError` now raise. On top of that, the pool watches the connection's round-trip odometer and refuses to replay a non-idempotent block that has already completed one round trip — redis-client re-dials mid-block, so a `CannotConnect` can surface on the *second* pipeline of a block whose first one already landed, and no per-command proof covers the commands ahead of it. Blocks that are genuinely safe to re-run pass `idempotent: true` (see *Added*). Every retry, refused replay and final give-up still reports through `Wurk::Configuration#on_redis_error`. (#353)
- **`Wurk::Client::Buffered::Overflow#payload` → `#payloads`** (Array). The exception now carries *every* undelivered payload rather than the single one that tripped the cap. Callers doing `rescue Overflow => e; Outbox.create!(payload: e.payload)` become `e.payloads.each { … }`. See [`docs/reliability.md`](../reliability.md#the-durability-caveat).
- **A poison-pill kill now notifies death handlers.** When the reliable fetcher's recovery counter crosses `RECOVERY_THRESHOLD` the payload goes to the dead set — but it went there with `notify_failure: false`, so nothing downstream ever heard about it. `Wurk::Batch::DeathHandler` *is* a death handler, which meant a poison-killed job never decremented its batch's pending count: `:death` never fired, `:complete` never fired, and the batch hung forever with no error recorded anywhere. The kill now runs the death-handler chain with a `Wurk::Middleware::PoisonPill::Poisoned` exception whose message names the class and the recovery count (`"MyJob was recovered 3 times without completing"`), which is also what `:death` batch callbacks and any error reporter will see. Every other terminal path in Wurk — retry exhaustion, `:discard`, the limiter's reschedule cap — already notified; a poison kill is the same kind of event. Sidekiq Pro's spec is silent on the question, so the choice is recorded in [`docs/idea/parity-divergences.md`](../idea/parity-divergences.md).
- **`Batch#on` deduplicates identical callbacks and caps a batch at 1,000 of them.** Re-registering the same `[event, target, options]` triple is now a no-op instead of appending a second copy, and past `Wurk::Batch::CALLBACKS_MAX` (1,000) the registration is refused with a logged warning. The shape this exists for is common and quietly quadratic: reopening a batch by bid inside every job and calling `on(:success, …)` there re-encodes the whole `callbacks` array on every append (O(N²) Lua work on the way in) and then enqueues N identical callback jobs when the event fires. The dedup is applied on both sides of the first flush — in-memory before it, in `BATCH_APPEND_CALLBACK` after — and normalises both sides through cjson, so `{a: 1}` and `{'a' => 1}` are recognised as the same callback. (#357)
- **Concurrent limiter — `held` and `overages` now mean what the documentation says.** `held` was never written on acquire at all; it is now bumped inside `limiter_concurrent_acquire.lua`, atomic with the `ZADD` (so a process dying mid-acquire can't undercount) and costing no extra round trip. `overages` counted acquires that exhausted `wait_timeout` — but that path raises `OverLimit` and is already counted per job in `overrated`. It now counts what the release script's contract says it counts: a holder that outran `lock_timeout` and found its slot already reclaimed when it released. Dashboards and alerts reading either counter will see different numbers after upgrading. (#355)

### Fixed

- **Swarm — a forked child could `SIGKILL` its own siblings on exit.** The child inherits the swarm object *and* `rails_boot`'s `at_exit { swarm.shutdown }`, so `ChildBoot`'s `exit` ran a full parent-style drain from inside a child, where `@children` holds its *siblings*: TERM to all of them, a 30-second stall waiting on pids it can never reap, then SIGKILL. One child exiting for any reason took the fleet with it. `boot` now records `@owner_pid` and `shutdown` / `supervise` / `safe_kill` no-op off it, and the `at_exit` registers before `boot` and only sets a flag the supervise thread observes. (#344)
- **Swarm — `can't add a new key into hash during iteration` under respawn.** `@children` and the restart state machine were touched from the supervise thread, the signal thread and the exit path at once. Both now live behind one reentrant `Monitor` (they are mutually recursive, so separate locks deadlock), readers walk snapshots, and `hard_kill_stragglers` kills and clears atomically. (#344)
- **Swarm — `USR2` reopened the children's logs but not the parent's.** The parent relayed the signal and never reopened its own descriptors, so after a logrotate the master kept writing into the deleted inode. It now reopens and relays. In the same pass, `shutdown` closes both ends of the self-pipe, `emit_signal` / `read_pending_signal` tolerate the pipe vanishing mid-drain, and `CLI#run` closes its pipe on every exit path and always drains the swarm. (#344)
- **Swarm — the parent reopened Redis sockets it had just closed before forking.** `heartbeat_seen?` ran on the capsule's main pool, so at concurrency ≥ 10 it re-opened, in the parent, exactly the sockets `close_parent_sockets` had shut — and every later respawn or restart fork inherited them. It now uses a dedicated single-connection pool that is disconnected immediately before every `Process.fork`, restoring the documented boot ordering. (#344)
- **Launcher — the shutdown tail leaked whatever the first failing step left behind.** `Launcher#stop` ran its teardown as a straight sequence, so one raising release step skipped every step after it. The whole tail now runs under `ensure` with each release independently guarded; the `TimerLoop`-driven components (`History`, `Metrics::Rollup`, `Metrics::QueueRollup`, `Scheduled::Poller`, `Cron::Poller`) join their thread with a bounded timeout and clear it on terminate instead of abandoning it; the heartbeat's stop handshake uses a `Mutex` + `ConditionVariable` rather than a `Thread#wakeup` that is lost if the target is not yet asleep; and `stop` joins the boot-time reclaim thread (bounded) before the rest of teardown touches Redis. (#346)
- **Launcher — a partial embedded boot left orphan threads running forever.** If `Wurk::Embedded#run` raised part-way, the host application was told Wurk never started while whatever the launcher *had* got up kept fetching, beating and campaigning for the leader lock, unowned, for the life of the process. A failed boot now rolls itself back (reporting a rollback failure separately so the caller still sees the original error), and `at_exit` registers before `run`. Embedded `#stop` also disconnects the configuration's Redis pools, so a stop-then-run cycle in a long-lived host no longer doubles the socket set on each pass; this is scoped to embedded mode, where the host outlives Wurk. (#346)
- **Launcher — a failed Processor replacement killed the host application's main thread.** When `Manager` could not spawn a replacement for a dead Processor (a `ThreadError` at the OS thread limit, typically) it called `Thread.main.raise`. That unwound straight past `Manager#stop`, so the in-flight `UnitOfWork`s were never `bulk_requeue`d and each one waited out a full reaper interval — and in embedded mode it killed the host's main thread rather than just the worker. The Manager now asks its owner to shut the process down through the normal path: a swarm child or standalone CLI re-delivers TERM to itself so the installed trap drives a real drain, embedded mode stops the launcher in place. `Manager.new(capsule)` keeps its old arity. (#346)
- **Fetcher — all queues paused turned every processor thread into a hot loop.** `Processor#run` drives `process_one` in a bare `until @done` loop with no pause of its own, so any `nil` returned instantly spins. `Fetcher::Reliable#retrieve_work` returned `nil` immediately when `queues_cmd` came back empty — which is what a fully paused (or unconfigured) queue set looks like — costing an `SMEMBERS` on the main pool per pass, as fast as the CPU allows: ~3,000 Redis calls a second per process, measured. It now sleeps a full poll interval on that path, and a short `QUIET_PAUSE` on the quieted short-circuit (`Manager#quiet` terminates the shared fetcher before the processors, so there is a window where every processor sees an instant `nil`). The pause is kept below `Manager::PAUSE_TIME` so it adds no drain latency. (#348)
- **Iterable jobs — an interrupted job resumed *behind* the entire backlog.** `InterruptHandler` re-pushed the job with `LPUSH`, described as "head of queue, so it is fetched next". It is not: the reliable fetcher's `LMOVE` pops from the *right*, so an `LPUSH`'d job goes to the back of the line and a long-running iterable job resuming after a restart waited out every job enqueued before it — including ones enqueued *after* the interrupt. The re-push is now `RPUSH`, which is genuinely next. (#348)
- **Reliable fetch — the reaper mistook a container restart for a live worker (and vice versa).** Private-list keys were `queue:<q>|<host>|<pid>|<idx>`, and the fast liveness check was `Process.kill(0, pid)` for any key whose host matched ours. Under a container restart into a fresh PID namespace, or `hostNetwork` sharing without PID-namespace sharing, that pid means nothing in our namespace: a dead owner's pid can be alive here (its jobs are never reclaimed and sit stranded until something else notices) and a live owner's can be free here (its private list is drained out from under it and its in-flight jobs run twice). The key now carries `Component::PROCESS_NONCE` — `queue:<q>|<host>|<pid>|<nonce>|<idx>` — and `kill(0)` is used only when the nonce is our own; every other incarnation falls through to the namespace-blind heartbeat check (`processes` SET membership), which waits out the 60s TTL exactly as the spec describes. The reaper parses both the new five-part and the legacy four-part key shape, so a rolling upgrade does not strand jobs written by not-yet-upgraded processes; the ambiguity is resolved by trying the wide reading first and taking whichever leaves a real public-queue name behind. Pid reuse within one namespace remains the documented blind spot, matching Sidekiq Pro's `super_fetch`. (#349)
- **`reliable_push!` replayed jobs Redis had already accepted.** A push is several round trips — one pipeline per destination queue, then the batched `BATCH_PUSH` pipeline — but the outage buffer took the whole payload set whenever any of them raised. A `push_bulk` spanning two queues that lost the connection after the first `LPUSH` landed, or any mixed plain + batched push whose batch phase failed, re-buffered payloads that were already enqueued and ran them a second time on the next drain. `Wurk::Client` now records each queue group as its reply comes in and `Buffered` re-buffers only the residual. The group in flight when the socket drops stays at-least-once (a lost reply is indistinguishable from a lost command); everything confirmed before it is not replayed. See [`docs/reliability.md`](../reliability.md#client-side-redis-outage-buffering).
- **`reliable_push_overflow = :raise` silently dropped payloads.** `Buffered.enbuffer` raised from *inside* its append loop, so a bulk push that crossed the cap buffered the payloads before the offending one, raised carrying only that one — and left every payload after it neither buffered, nor enqueued, nor referenced anywhere. A 1000-job `perform_bulk` against a nearly-full buffer lost up to 998 jobs with no error naming them. The split is now decided against remaining capacity before anything is appended: the buffer takes what fits and one `Overflow` carries the rest. The same raise also pre-empted the `bid`-carrying re-raise, stranding batched payloads (which never buffer) in a mixed push; they are now folded into the same exception, with `cause` still the connection error.
- **The outage buffer was not fork-safe — every swarm child replayed the parent's buffered jobs.** The buffer, its drainer and both of its mutexes are process-global and were copied wholesale into each child, so a fork taken while jobs were buffered enqueued the lot once per child *plus* once from the parent: `(children + 1) × N` duplicates. Worse, a fork taken from inside either critical section left the child holding a mutex whose owner thread did not survive, and its first `Client#push` (which drains, so it synchronizes, before pushing) blocked forever. `Buffered.reset_after_fork!` now rebuilds the buffer, drainer and mutexes per process, driven from both the `Process._fork` hook and `Swarm::ChildBoot#reconnect_after_fork` (whichever runs first wins; the pid guard makes the other a no-op). The child *drops* its inherited payloads rather than replaying them — the parent still holds the same buffer and replays it on its own next push — and a parent-configured drainer is replaced by an equivalent fresh one so an opted-in child keeps flushing what it buffers itself. In the same pass the drain pool is resolved late through the configuration instead of a pinned pool object, and `emit_enqueued` stopped double-counting buffered pushes as both enqueued and recovered. (#352)
- **Five Redis call sites replayed a write that may already have applied.** These are the concrete losses the retry-policy split above exists to prevent, each confirmed and fixed with fault-injection coverage: `Client#atomic_push` re-pushed a job whose `LPUSH` reply was lost (a duplicate job), `Scheduled#zpopbyscore` re-ran a pop whose reply was lost (a *lost* scheduled job — the members it popped were already gone), `Launcher#write_stats` double-counted processed/failed counters, `Heartbeat#drain_signals` dropped a dashboard-issued TERM/TSTP on the floor, and `PoisonPill#bump_counter` double-incremented a recovery counter and could kill a job one reclaim early. A real-TCP-blip integration test now asserts a seeded `<identity>-signals` entry survives a heartbeat retry exactly once — no drop, no duplicate. (#353)
- **Leader election — releasing the lock could delete somebody else's.** `Leader#release` was `GET` then `DEL`. Between the two, our own key can lapse and a follower can win the election — and the bare `DEL` then deletes *that* process's lock, leaving the cluster leaderless (or, once the ex-leader re-campaigns, doubly led) for up to a renew interval. Double leadership means double cron fires and double metric rollups. The compare and the delete now happen in one server-side step, through the `release_if_owner` script `Wurk::Unique` already shares. (#354)
- **Leader election — two racing `start` calls leaked an unkillable second campaigner.** The nil-check ran inside the mutex but the thread spawn ran outside it, so both callers could pass the check and both spawn; the loser's thread was never recorded in `@thread`, survived `stop`, and went on renewing the cluster lock forever. The spawn now happens inside the lock (the same pattern the Reaper uses). (#354)
- **Periodic — a leader handover could fire the same schedule slot twice.** The leader gate is a cached read, so for a few seconds after a handover two pollers can both believe they lead and both reach the same due loop. Each then read the `lf`/`nf` fire marks, enqueued, and wrote the marks back — a read-modify-write with no arbitration. The marks now advance through a single-Lua compare-and-swap (`cron_claim_fire`) *before* the enqueue, so only the tick still looking at the mark it read owns the slot. The consequence of putting the claim first is that a failed push drops that occurrence rather than risking a duplicate one; the drop is logged with the lid and class. Manual `Cron#fire` deliberately skips the CAS — an operator-requested run contends with no schedule slot. (#354)
- **Window limiter — reading `status` from the dashboard could wipe a live window.** `Window#size` and `#status` computed their cutoff from the *calling host's* clock and then `ZREMRANGEBYSCORE`d against it, on every dashboard GET. A web host running more than one interval ahead of Redis therefore evicted live entries just by rendering the page, and the next callers charged the limit a second time. Both are now genuinely read-only: one `ZCOUNT` + `ZRANGEBYSCORE` in a read-only Lua script deriving the cutoff from Redis's own `TIME`, in a single round trip. Trimming stays exclusive to the acquire script, which still enforces the limit after any skewed read. (#355)
- **Bucket limiter — a waiting job busy-polled every 50 ms instead of sleeping to the boundary.** `secs_to_next` was computed and then discarded inside a `.min` that could never select it, so the wait loop woke twenty times a second for the whole wait. It now sleeps toward the next cardinal boundary (floored at 50 ms, clamped to the remaining deadline). (#355)
- **Batches — sub-keys were created without a TTL and leaked permanently.** Only `b-<bid>` was stamped at first flush; `-jids`, `-failed`, `-died`, `-kids`, `-pkids` and the callback dedup markers were created later, by the Lua push scripts, `link_to_parent` and `record_event`, with no expiry at all. Every one of them outlived its batch forever. Each is now stamped `EXPIRE … NX` at its creation site (NX so a live batch's expiry, and the shorter post-success `linger` window, are left alone), `DeathHandler.restamp_ttls` sweeps the rest on death, and `record_event` re-stamps a hash it resurrects — a child batch's callback firing after the parent's 30-day window had lapsed used to recreate `b-<bid>` with no clock on it at all. `Batch::KEY_SUFFIXES` also gained `complete`/`success`/`death`, the three dedup markers Wurk actually writes, so `Status#delete` now sweeps them instead of leaving them behind. (#356)
- **Batches — the `batches` and `dead-batches` index ZSETs grew for the life of the Redis.** Only `Status#delete` and the death-recovery `ZREM` ever removed a member, and neither runs for a batch simply left to expire, so an index entry outlived by weeks the batch hash it pointed at — and `BatchSet` enumeration got slower forever. `Batch.trim_index` now runs in-pipeline with each `ZADD` (so bounding the index costs no extra round trip) and trims on two axes, in the same shape as the morgue trim: `ZREMRANGEBYSCORE` against the batch expiry window, plus a `ZREMRANGEBYRANK` backstop at `Batch::INDEX_MAX` (1,000,000). A batch that overrode `expires_in` past the default window is still reachable by bid, just no longer enumerated. (#356)
- **Batches — a crash could lose a `:complete` or `:success` callback permanently.** Both fired by claiming their dedup key first and enqueuing the callback second. Nothing ever re-drives that fire — once the acking job's `BATCH_ACK_SUCCESS` has `SREM`'d its jid, that job's retry gets `pending == -1` and returns before `maybe_fire` — so a crash in the window between the claim and the enqueue meant the callback was never enqueued by anyone, ever, and the batch silently stranded. The order is now enqueue-then-mark, with the read-side gate on the marker's existence, so the durable side effect happens before the marker that suppresses it. The accepted direction of the trade is a rare duplicate over a silent loss: callback jobs retry like any other job and are required to be idempotent, and sequential re-invocations (a reclaimed child re-running `propagate_to_parent`, a second `DeathHandler` pass) are still collapsed — the duplicate window is only two genuinely concurrent acks interleaving between each other's check and mark. `fire_death` deliberately keeps claim-before-enqueue: everything that makes a batch *look* dead is already persisted before the guard, so a crash there costs the notification but not the state. (#356)
- **`lmtr-list` grew one permanent member per limiter name.** The spec blesses interpolated limiter names (`stripe-#{user_id}`), which means a limiter is constructed per job and registration sits on the enqueue path — and registration `SADD`'d the name on *every* construction while `lmtr:<name>` expired with the limiter's TTL. The set therefore accumulated a member for every user, order or tenant the application had ever seen, and rendering the dashboard's Limits page got slower forever. Registration is now one Lua round trip (metadata `HSET` + `EXPIRE` + `SADD`, down from three) that only adds to the set when the `HSET` actually created the metadata, and `Web::Enterprise::Limits.list` sweeps names whose metadata has expired — batched at 512 names per pass so a set that leaked for months cannot block every other Redis client for the length of one atomic call, and re-deciding liveness inside the script so a name that re-registers mid-sweep is not hidden until its TTL runs out. (#357)
- **Poison pill — the recovery counter was never cleared, so three unrelated crashes dead-set a healthy job.** `super_fetch:recovered:<jid>` was incremented on every reclaim and only ever decayed on its 72-hour TTL. Nothing reset it on success — and jids do come back: a dashboard or API retry re-pushes the same one, as does any client that supplies its own. Three reclaims caused by three *unrelated* events inside one window — a deploy `SIGKILL`, an OOM kill, a node eviction — therefore moved to the dead set a job that had completed every single time it ran, with `notify_failure: false` so nothing said so. The counter is now retired by the ACK: `Fetcher::Reliable::UnitOfWork#acknowledge` pipelines the `DEL` next to its `LREM`, so an attempt that finished — returned, or raised and booked its retry — starts the next one at zero, and it costs no extra round trip for the jobs (nearly all of them) that were never reclaimed at all. Only an attempt that never acked, because the process died under it, still accumulates, which is precisely the signal the counter is meant to carry. A fetcher plugged in through `config[:fetch_class]` whose unit of work has no `jid` slot simply ACKs as before; its counters age out on the TTL. `Wurk::Middleware::PoisonPill.clear!(jid)` remains available for clearing one by hand.
- **Dashboard — SPA resource leaks on unmount.** An extension page navigated away from mid-fetch left the request in flight and called its setters into a disposed component; it now aborts through an `AbortController` on cleanup. Toast timers were never cleared (a dismissed toast still held a 6-second timer, and a burst of failures grew the list unbounded) — timers are cleared on dismissal and on eviction, and the list is capped at five. `Modal` children are memoized so closing one releases the held subtree instead of retaining it. `prefers-reduced-motion` is now a reactive signal with a listener cleaned up on unmount, rather than a value read once at mount, so toggling the OS setting takes effect without a reload. (#351)

### Upgrading

- **`Wurk::Client::Buffered::Overflow#payload` is gone; use `#payloads`.** It is an Array now, carrying every undelivered payload rather than only the one that tripped the cap. Any `rescue Wurk::Client::Buffered::Overflow => e` handler that reads `e.payload` raises `NoMethodError` after upgrading — grep for it before deploying. Applications that only rescue and log are unaffected apart from the message text, which now names the count. This only applies if you have enabled `reliable_push!` with `reliable_push_overflow = :raise`.
- **Read and write timeouts are no longer retried by default.** A `RedisClient::ReadTimeoutError` or `WriteTimeoutError` that the pool used to absorb with exponential backoff now propagates to your code. In practice the fetch loop, the scheduler and the heartbeat all already rescue and re-loop, so the visible change for most applications is *fewer* duplicate jobs and more `on_redis_error` reports — but a bespoke `Wurk.redis { … }` call site in application code that relied on the pool swallowing a slow-Redis blip will now see the exception. If such a block is genuinely replay-safe (a pure read, an owner-CAS script, a `SET` of a constant), pass `Wurk.redis(idempotent: true) { … }` to restore the old behavior. Do not pass it for `INCR`, `LPUSH`, `ZADD` or anything else whose repeat changes state — that is the duplicate-job bug the split fixes. Connection *failures* (`CannotConnectError`, `FailoverError`) and the `READONLY` failover path are unchanged and still retry.
- **Private-list keys gained a segment: `queue:<q>|<host>|<pid>|<nonce>|<idx>`.** No action is required — the reaper parses both the new five-part shape and the legacy four-part one, precisely so an upgrade does not strand in-flight jobs written by processes that have not restarted yet. Be aware that during a rolling deploy the keyspace holds both shapes at once, and that any external tooling, dashboard or alert that parses these keys positionally needs teaching about the extra segment before it starts mis-reporting owners. Nonce-mismatched owners (which is every pre-upgrade process, from an upgraded process's point of view) are judged by the 60-second heartbeat rather than by `kill(0)`, so reclaim of a crashed old-format worker can take up to a minute longer than it used to during the deploy window. Once every process has restarted, the fast path is back.
- **Poison-pill kills now fire death handlers, so your error reporter will see a new event class.** A job killed after `RECOVERY_THRESHOLD` (3) reclaims previously went to the dead set silently; it now runs the death-handler chain with a `Wurk::Middleware::PoisonPill::Poisoned` exception. Sentry, Honeybadger, a custom `config.death_handlers` entry and any `:death` batch callback will start observing these — that is the point (a stranded batch used to be the alternative), but budget for the alert if your reporter pages on new issue types. Note that the fix above means far fewer jobs reach the threshold in the first place, so the expected volume is low. If you need to suppress the notification for a specific class, filter on `Wurk::Middleware::PoisonPill::Poisoned` in your reporter.
- **Concurrent-limiter counters changed meaning.** `held` is now written on every successful acquire (it previously was not written at all, so any dashboard panel or alert reading it was reading a permanent zero), and `overages` now counts holders that outran `lock_timeout` rather than acquires that exhausted `wait_timeout`. The latter is still counted, per job, in `overrated`. Repoint any alert threshold accordingly.
