# 1.17.1 — 2026-11-21

### Fixed

- **Sidekiq Pro's private lists are reclaimed.** Pro 7.3 keeps in-flight jobs in `queue:sq|<host>:<pid>:<nonce>|<queue>`. Wurk could not read that name, so the jobs of a Pro process that died before the cutover stayed there, reported as unparseable. The reaper now returns them to their queue, keeping a `|` in the queue name.
- **A Pro list could be drained from a live owner.** A Pro queue name ending in `|<digits>|<digits>` was misread as a Wurk list on a queue called `sq`, so its owner was judged by a heartbeat that does not exist and its jobs moved to the wrong queue. A name that reads as both shapes is now refused and reported.
- **A public queue whose name reads as a private list is no longer drained.** The reaper checks the `queues` set before it treats such a key as orphaned.
- **A private-list key with invalid UTF-8 no longer aborts the reaper's sweep.** It is reported as unparseable.
- **A Redis failure after `perform` returned no longer runs the job again.** Since 1.16.0, a connection error in the bookkeeping after `perform` (a sidekiq-unique-jobs unlock, a batch ack) put the job back on its queue up to 3 times per process, even with `retry: false`, so a bank login or an email could repeat. The job is now ACKed and counted as processed at any `retry` setting, and the error goes to your error handlers as `Wurk::FinishedJobCleanup::BookkeepingFailed`, with the Redis error as its `cause`. The same holds for any Redis error reply there (`READONLY`, `OOM`, `WRONGTYPE`) and for a hard shutdown landing after `perform`.
- **A Redis connection error can no longer replay `perform`.** sidekiq-unique-jobs runs `perform` inside a `Sidekiq.redis` block, and the pool replays a block after a connect error, so a failed unlock on `while_executing` or `until_and_while_executing` could run the job a second time inside the same attempt. A block that ran a job is never replayed.
- **A lock or batch ack missed in an outage is finished when Redis returns.** The worker keeps the failed sidekiq-unique-jobs unlock and batch success ack in memory and retries them before each fetch, so a job's lock no longer blocks its next run until the TTL. Only a lock this job holds is released. A process that stops first logs each lock it left, by digest.

- **The sidekiq-unique-jobs reaper keeps the lock of a job in a private list.** After a `kill -9` and once the worker's heartbeat expired, the gem's reaper saw no job for the lock and deleted it, so a duplicate was accepted and ran beside the recovered job. A job in any private list, Wurk's or Sidekiq Pro's, now counts as live.
- **A worker can boot with Redis or Dragonfly at `maxmemory`.** An OOM on sidekiq-unique-jobs' version write at startup stopped the worker, so a deploy at the ceiling crash-looped with nothing draining the queues. That one write is now logged with its key and value and skipped. A lock write refused by OOM still raises, so a push is never treated as locked.

### Upgrade notes

- A Pro list is reclaimed only after its owner's heartbeat hash (`<identity>`, field `info`) has been gone for the reaper's grace. Heartbeats cannot see a process that is running but cut off from Redis for longer than that, so **stop every Pro worker before starting Wurk**.
- A reclaimed job runs again, as it would under Pro. A job that was killed partway through must be safe to repeat.
- A process killed before its ACK reaches Redis still re-runs that job, as on every version and under Sidekiq Pro.
- No Redis key, job format or configuration change.
