# Unreleased

### Changed

- **`CurrentAttributes` writes `cattr` in Sidekiq's shape.** `Sidekiq::CurrentAttributes.persist` now stores each class's attributes as `ActiveJob::Arguments.serialize(attributes)`, an array of `[name, value]` pairs, where it used to store a plain JSON object. A Symbol, a Time or a record (GlobalID) comes back in the job as itself, and a job enqueued by Sidekiq restores under Wurk and the reverse. The plain object Wurk wrote before is still read. `persist` now requires ActiveJob (`require "active_job"`), and an attribute the class no longer defines is skipped on load instead of raising. See the upgrade note below and `docs/middleware.md`.
- **`Sidekiq.testing!` refuses an unknown mode.** Anything but `:fake`, `:inline` or `:disable` raises `Unknown testing mode: …`, as Sidekiq does, instead of being stored.
- **The shared health port being taken logs at INFO in a swarm.** One child owning the port and the others polling to take it over is the normal case there. A lone process still logs it at WARN.

### Fixed

- **Batch callbacks survive a Redis restart.** A job that finished while Redis was restarting gave up acknowledging its batch, or firing the batch's callbacks, after three attempts inside 150 ms, was ACKed, and nothing fired the drained batch again. The ack, the fire and the death record now wait out a store that is not serving (connection errors, `LOADING`, `BUSY`, `READONLY`, `CLUSTERDOWN`, `MASTERDOWN`, `TRYAGAIN`) for up to 5 minutes before reporting the failure. A retry after a partial enqueue pushes only the callbacks that failed, not the ones that already landed.
- **A unique lock is released when the push it guarded never happens.** When a client middleware after the unique check halted the push or raised, the lock stayed until its TTL and every enqueue of the same arguments was dropped as a duplicate. A lock taken by that push is now released; a re-push that finds its own jid holding the lock leaves it alone.
- **A points limiter refund no longer empties a reset bucket.** A refund arriving after the limiter's state was reset or expired counted the missing bucket as empty, leaving it holding only the refunded points. It is now read as full, as the acquire script reads it.
- **Requeuing a fetched job gives its global-concurrency slot back.** `UnitOfWork#requeue` called from outside the Processor (a throttling fetch wrapper) kept the slot held for the life of the process.
- **A child respawned while the swarm is quiet fetches nothing.** It was quieted after its launcher started, so jobs claimed in between ran during the maintenance window. It is now quieted first.
- **Stopping the `reliable_push!` drainer no longer stalls or restarts it.** A replay failing during the stop waited on the lock the stop held, for the whole join timeout, and then started a new drainer.
- **`config.concurrency = "10"` sets 10.** The value is coerced with `Integer()`, so a count read from an environment variable is stored as a number; a non-numeric one raises `ArgumentError` at the assignment.
- **`Sidekiq.logger = nil` silences the logger.** It raises the current logger's level to `FATAL`, as Sidekiq does. It used to discard the logger, and the next read built a default one that logged again.
- **`set(wait: nil)` and `set(wait_until: nil)` enqueue now** instead of raising, and `wait_until` wins when both are given.
- **`MyJob.jobs` is the live array.** It returned a copy, so `expect { … }.to change(MyJob.jobs, :size)` never saw the push. `Sidekiq::Queues.jobs_by_class` is live too.
- **`Sidekiq::Logger::Formatters::Plain` exists**: `Pretty` without the ANSI colour codes.
- **A `unicorn` Gemfile entry no longer counts as a preforking server.** The railtie refused to boot workers under `rails server` or Puma single mode when the unicorn gem was merely loaded. Only a process started as `unicorn` counts now.
- **An iterable job resumes after the last item it finished.** The cursor is now checkpointed before its item runs, as Sidekiq does, so an interrupt between items no longer re-runs the last completed one (a whole batch for the ActiveRecord batch enumerators), and an item that raises is retried from itself. Cursors read and written are the same values Sidekiq uses, so a job interrupted under either resumes under the other. See the upgrade note.
- **Retrying a job from the Retry, Scheduled or Dead set always writes to Redis.** `SortedEntry#retry`, `#add_to_queue` and `retry_all` pushed through the client, which during a `reliable_push!` outage buffers in process memory: a job removed from the set could be lost if that process then crashed. They now push unbuffered, as the scheduler does.
- **`Wurk::Cron.register(..., tz:)` fires in that zone.** The zone was stored but the loop fired in UTC. After a change of zone alone, the next fire still happens on the old zone's clock once; every later one follows the new zone.
- **A missed periodic tick says how many fires it skipped** (`skipped=N`), instead of one line that read as a single miss.
- **Missing Sidekiq API:** `Sidekiq::Capsule#[]`, `#[]=`, `#fetch`, `#key?`, `#has_key?`, `#merge!`, `#dig`; `Sidekiq::Stats#fetch_stats!`, `#fetch_stats_fast!`, `#fetch_stats_slow!`; and `RetrySet#take(n)` (and the other job sets) is `Enumerable#take` again; a private helper shadowed it.
- **A Redis outage after a job's `perform` returned no longer fails the job.** A batch ack or other bookkeeping write hitting a connection error, `LOADING` or `BUSY` killed a `retry: false` or last-attempt job and marked its batch dead for good. The job now goes back on its queue and runs again, which is the same at-least-once delivery a lost ack already gives, up to 3 times per process; after that the retry policy decides, so a store that stays broken cannot re-run `perform` forever. `docs/idea/parity-divergences.md` records the difference from Sidekiq.
- **A batch callback job is never held in the `reliable_push!` memory buffer.** A callback buffered during an outage was lost if the process crashed before the buffer drained, and its dedup marker kept it from firing again. The push now raises, and the batch's outage wait re-drives it.
- **One bad buffered job no longer blocks every push.** A `reliable_push!` replay that Redis refused because of the entry itself (`WRONGTYPE` on its queue) failed the whole slice, and from then on every push to that Redis. Such an entry (`WRONGTYPE`, or a payload that cannot be serialized) is now reported to the error handlers with its jid and dropped; the others are delivered. Any other error reply keeps every entry, as before. A job whose `LPUSH` landed before a later write failed is not pushed twice.
- **The scheduler restamps only the job's own `enqueued_at`.** Promoting a scheduled or retry job rewrote the first `"enqueued_at":` number in the payload, which could be inside the job's arguments.
- **The `/v1` API answers a Redis outage with 503 `redis_unavailable`** and `Retry-After: 1`, where it answered 500 `internal_error`. A Redis error reply is still a 500.
- **The dashboard API answers 400 for a queue-job delete without a jid**, where it answered 500.
- **Dashboard: one failed poll no longer blanks the page.** Queues, Busy, Limiters, Flows, Cron and Profiles keep showing the last data loaded, and any open modal, under an inline notice. The full error state is kept for a page that has loaded nothing yet.
- **Dashboard: rows that open a detail view work from the keyboard.** Queue, job, process and periodic-job rows are focusable, open on Enter or Space, and show a focus ring.
- **Dashboard: tooltips show on keyboard focus**, not only on hover, and Escape dismisses them.
- **Dashboard: the Batches tag filter follows the URL.** Browser Back to a different `?tag=` left the old text in the box.
- **Dashboard: bulk actions on Retries, Scheduled and Dead reach only the selected rows still shown.** A row selected and then paged or filtered away was still counted and acted on.
- **Dashboard: the overview counters keep moving after the live stream drops.** The stream's last snapshot was preferred over newer polled data.
- **Dashboard: a failed load is not shown as empty.** The Dashboard and Metrics charts and the Metrics job table show the error when nothing loaded, and the Metrics counters show `—`, where they showed "no history", "No items" and `0`.
- **Dashboard: Busy marks a process whose heartbeat stopped.** The heartbeat indicator was only judged when a row's data changed, which a stopped process's never does.
- **Dashboard: a job's action buttons disappear when read-only mode is detected** after the job detail modal was built.
- **Dashboard: a custom tab's form submits the button that was pressed**, so a view with several named submit buttons gets the one clicked.
- **Dashboard: profile routes answer 404 for a key that is not a stored profile.** `/profiles/:key` and its data route took any Redis key: a non-hash key returned a false 503, and any hash with a `data` field could be sent to the profiler.
- **Dashboard: the Busy badges and the overview queue table's "Name" header are translated.**
- **The demo lock is off the puma reactor advisories.** `demo/Gemfile.lock` moves puma from 8.0.2 to 8.1.2, above the `>= 8.0.3` floor for GHSA-m5xw-3hrw-qcmf (a reactor timeout queue that loses order, letting a slow client keep other connections open past their timeout), GHSA-xw3h-pgr9-3vg7 and GHSA-jm4r-w4xx-qxw7. The demo image installs the lock frozen, so this is what it ships; puma's only runtime dependency, `nio4r`, is unchanged.

### Upgrade notes

- **`CurrentAttributes` during a rolling upgrade.** Applies only if you call `Sidekiq::CurrentAttributes.persist`. While both versions run, a job enqueued by the new version can be fetched by a worker still on the old one, which reads the new `cattr` pairs without deserializing them: an attribute that is a Symbol, a Time or a record arrives in its serialized form, so the job can fail once there and succeed when its retry lands on an upgraded worker. Attributes that are JSON-native (strings, numbers, booleans) restore on both. To avoid it, upgrade the workers before the processes that enqueue. Jobs written by the old version restore on the new one.
- **`CurrentAttributes` needs ActiveJob.** A non-Rails app that calls `persist` needs `activejob` in its Gemfile.
- **Custom iterable enumerators yield the item's own cursor.** If you wrote a `build_enumerator` that yields `[item, next_position]`, it now skips one item after each interrupt, exactly as it would under Sidekiq. Yield the position that, passed back as `cursor:`, starts at that item (the built-in enumerators already do). `docs/iterable-jobs.md` has the contract.
