# 1.21.0 — 2026-11-25

### Changed

- **A job interrupted at the shutdown deadline is requeued as its own thread ends, not before.** It was on its public queue, and running in another process, while its own `ensure` blocks were still rolling back and releasing limiter slots. A thread that has not ended within 2s has its job requeued while it runs, inside the grace the swarm already allows; the payload stays in the private list meanwhile, so a SIGKILL loses nothing. Interrupted before its `perform` completed, a job is requeued whatever it made of the interrupt, and books no retry for it; one that had completed, or whose retry was booked, is not run again as well. A `config[:fetch_class]` fetcher that is not a `Fetcher::Reliable` keeps the old order ([reliability](../reliability.md#graceful-shutdown)).

### Fixed

- **sidekiq-unique-jobs, native: an interrupted run no longer releases the lock its own re-run holds.** The holder was known by jid, so when a requeued or reclaimed job ran again while its first run was still unwinding, that unwind deleted the lock and a third job ran beside the second; `refresh_lock!` told both runs they held it. Each run now marks the lock it enters (the time beside its jid in `:LOCKED`, so nothing new in Redis) and only the newest mark unlocks or renews, for `while_executing`, `until_executed` and `until_and_while_executing`; a job still re-enters the lock of a run that crashed. An unlock owed after a Redis outage is held to the same. Processes on Wurk 1.20 or the gem neither write nor check marks, so the deploy that brings this in still has the old exposure ([two runs of one job](../unique-jobs.md#two-runs-of-one-job-wurk-only)).
- **sidekiq-unique-jobs, native: a job cut short by a shutdown keeps its runtime lock** and re-enters it when it is requeued, instead of giving it to a waiting job and coming back to a conflict. An interrupted `until_and_while_executing` job is no longer dropped when its successor was already queued. Differs from the gem, which releases the lock and drops the job.
- **A finished job whose unlock a full Dragonfly refuses is not failed for it.** Dragonfly words the refusal as a failed script, which read as the job's own error and booked a second run. It now waits for the store like the same refusal from Redis.
- With json 3.2.0, whose `script_safe` no longer escapes `/`, a job class or queue holding a `/` was counted in `stat:deaths` under two fields, one written by Ruby and one by the schedule-promote script. Before 3.2.0 the same held for `U+2028` and `U+2029`. Both write the same field again. `/metrics` sums the two spellings already stored.
