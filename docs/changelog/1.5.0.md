# 1.5.0 — 2026-08-07

A performance release, and the first one to publish honest numbers against stock Sidekiq rather than a slogan. The fetch path went from ~4 Redis round trips per job to ~1, the swarm parent now warms the Lua cache once for the whole fleet instead of once per child, and a resource-lifecycle audit closed the leaks and shutdown races that only show up in a process that has been up for a week. Three of the round-trip wins are behavior-visible and are documented as intentional divergences — read *Changed* before deploying. The "Faster." claim is gone from the gem summary, the dashboard and every translation: wurk is currently **0.87×–1.02×** stock Sidekiq depending on workload, at parity on CPU- and I/O-bound jobs and still behind on framework overhead and boot. The numbers, the method, and the command to reproduce them are in [`docs/benchmarks.md`](../benchmarks.md).

### Added

- **`leader_initial_wait` — defer the first leader-election CAS.** A booting process used to spend some of its opening round trips on a `SET NX EX` campaign for the cluster leader lock. `Leader` now waits `leader_initial_wait` before its first attempt, so the job path gets those round trips instead; a shutdown arriving during the delay wakes on the same condition variable rather than waiting the delay out. Documented in [`docs/configuration.md`](../configuration.md). (#391)

### Changed

- **Fetch, ack and metrics batched down to ~1 Redis round trip per job (from ~4).** Three behavior-visible trades, all wire-compat (no key/field/score-format change), signed off in [`docs/plans/2026/08/06/101-faster-than-sidekiq/00-semantics-signoff.md`](../plans/2026/08/06/101-faster-than-sidekiq/00-semantics-signoff.md) and recorded as intentional divergences in [`docs/idea/parity-divergences.md`](../idea/parity-divergences.md):
  - **Paused-queue visibility across processes is now bounded at 2 seconds instead of immediate.** `Fetcher::Reliable` caches the paused-queue set behind a 2s monotonic-clock TTL instead of an `SMEMBERS` on every fetch pass. A `pause!`/`unpause!` issued from *within* the fetching process itself still takes effect on that process's next fetch pass; cross-process propagation is bounded by the TTL. `Wurk::Queue#paused?` and the dashboard/API still read Redis directly and are unaffected. In practice this does not move the fleet's worst case: an idle worker parked in `BLMOVE` already couldn't notice a pause faster than its poll interval (default 2s).
  - **Dashboard per-minute/per-class job counters now lag by up to 5 seconds, and a hard kill (`SIGKILL`, OOM, box loss) can drop up to 5 seconds of unflushed counters for that process.** `Metrics::History` accumulates counts in memory, keyed by the minute bucket computed at record time, and flushes on a ≤5s timer (plus on every graceful stop) instead of writing on every job. Bucket attribution is unaffected — only visibility lag, never misattribution. This was already a best-effort write path (a Redis failure here never affects a job's outcome); Sidekiq itself batches these on a 10s heartbeat and wurk's cadence is tighter.
  - **The redelivery window after a hard process death widens from "immediately after the job finishes" to "the next fetch, or the next flush point, whichever comes first."** A completed job's `LREM` off the private list is now held by the fetcher and piggybacked onto the next `BLMOVE`/`LMOVE` pipeline instead of sent as its own round trip. Wurk is still at-least-once and a job is never lost; what widens is the same duplicate-execution window `docs/reliability.md` already documents, not a new failure class, and it's unreachable by a graceful shutdown (acks flush before `bulk_requeue`, before blocking, before `terminate`). Idempotent job handlers remain the required mitigation, unchanged.
  - Net effect measured in [`08-measurements.md`](../plans/2026/08/06/101-faster-than-sidekiq/08-measurements.md): commands/job 10 → 3 (one round trip), `fetch+execute` 1.41k → 2.53k i/s.
- **The swarm parent loads Lua once for the whole fleet.** `Swarm#boot` runs `script_load_all` on the supervisor pool between `close_parent_sockets` and the fork loop, so the children inherit a warm `EVALSHA` cache instead of each re-uploading all 25 scripts; `ChildBoot#validate_redis!` keeps only its `PING`. Measured server-side (`INFO commandstats`) across five 8-child boots: **1000 → 125 `SCRIPT` calls** (200/boot → 25/boot). A preload that never warmed, or a cache wiped by a Redis restart between the load and the fork, still self-heals on first use. In the same pass `Configuration#prepare_for_fork!` materializes every capsule's middleware chains and freezes `@options` in the parent, so children inherit warmed copy-on-write pages rather than each rebuilding them. (#391)
- **Each child starts fetching before it starts polling.** `Launcher#run` brings up the managers, heartbeat, reaper and boot-reclaim sweep first and the periodic loops second, so a freshly forked child is taking jobs while its background timers are still coming up. (#391)
- **The gem summary no longer claims "Faster."** `spec.summary` on RubyGems, the `Wurk` top-level docstring, the dashboard tagline in all eight locales, and the CodeRabbit review invariants all asserted wurk was faster than stock Sidekiq. It is not — see [`docs/benchmarks.md`](../benchmarks.md). The claim may not go back until the published numbers support it (CLAUDE.md pillar 3). No behavior change; this is the metadata and UI catching up with the measurements that landed in 1.4.0's wake.

### Fixed

- **`Stats::History` read a different day than `Launcher` wrote.** The writer keys `stat:processed:<day>` / `stat:failed:<day>` / `stat:expired:<day>` off `Time.now.utc`, but the reader defaulted its window to `Date.today` — the *local* civil date. On any host not running UTC, that asks for a day the writer never wrote for whatever slice of each day the offset spans: the newest bucket comes back `0` and the whole window is shifted by one. A dashboard on a UTC−5 host showed an empty or stale "today" for the last five hours of every day. The default is now `Time.now.utc.to_date`, matching the writer exactly; an explicitly-passed `start_date` is untouched.
- **Dashboard assets now send `Cache-Control`.** `Wurk::Engine::AssetMount` is inserted at index 0 of the *host application's* middleware stack, so `Rack::ETag` and `Rack::ConditionalGet` never saw its responses and the precompiled bundle was re-fetched in full on every page load. Fingerprinted assets are now cached immutably for a year; everything else revalidates. (#384)
- **Resource-lifecycle audit — leaks, shutdown races, and a supervisor that reaped too much.** Every fix carries its own regression test, mutation-checked against the pre-fix code (#392):
  - `Swarm#reap_children` / `hard_kill_stragglers` waited on *any* child pid, so in an embedded or standalone boot the supervisor could reap — and hard-kill — subprocesses the host application had spawned for its own reasons. Both now wait only on pids the swarm tracks.
  - Every shutdown join is now bounded (reaper, leader, the launcher's stoppers, embedded TERM handling), and `Launcher#stop` releases its Redis pools on every path rather than only when embedded.
  - `Processor::WORK_STATE` had a publish window where a job was running but not yet visible to the dashboard's Busy pane; it is now an RAII `track` frame. `Configuration#lookup` no longer raises `FrozenError` against a frozen `@directory`.
  - Four retention leaks: `PoisonPill.on_poison` now dedups by callable identity and returns a removable registration, `Heartbeat` stopped leaking a file descriptor per beat (`File.foreach` → `File.open`), `Web::Config#rack_app` re-keys its memo on `[inner, middlewares]` instead of serving a stale app, and `Client::Buffered#reset!` no longer orphans its drainer thread.
  - The SSE concurrency guard is self-healing: slots are scoped to thread identity instead of counted, so a hard-reaped stream thread no longer permanently 503s `/api/stream`.
- **A stale comment on `JobSet#schedule` described the opposite of the code.** It claimed `ZADD` with `NX` "so re-scheduling the same payload doesn't reset its score"; the call has no `NX` and never did. The behavior is correct and matches `Sidekiq::JobSet#schedule` — the last schedule call wins — so the comment was corrected rather than the code.

### Known issues

- `Wurk::Metrics::History` books a cooperatively-interrupted `IterableJob` as a failure, inflating the dashboard's failure rate for apps that interrupt iterable jobs across restarts. The chain ordering, the blast radius and the parity question that has to be settled first are in [#394](https://github.com/developerz-ai/wurk/issues/394). Rate-limited reschedules are *not* affected — the limiter middleware sits outside the metrics middleware and never yields to it.
