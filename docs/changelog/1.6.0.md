# 1.6.0 — 2026-08-09

A "beyond Sidekiq" release: eight Wurk-only extras, none of them Sidekiq parity. Every one is additive-only — off by default, zero Redis round trips on the hot path unless opted in, no existing Redis key, sorted-set score, or job-JSON field changed. Full plan and per-slice sign-off: [`docs/plans/2026/08/07/101-beyond-sidekiq/overview.md`](../plans/2026/08/07/101-beyond-sidekiq/overview.md).

### Added

- **Job status, progress & results (`Wurk::Status`).** Opt-in `sidekiq_options track: true` persists a `status:<jid>` Hash — lifecycle state, coalesced in-job progress writes (`Worker#status`, one write per 5s window), and the terminal return value (8 KB cap, withheld rather than stored plaintext when the job is also `encrypt: true`). Zero-cost when unset — one Hash lookup, no extra command. No `Sidekiq::Status` alias: the `sidekiq-status` gem owns that constant name upstream (see `lib/wurk/compat.rb`). [`docs/job-status.md`](../job-status.md). (#402)
- **HTTP producer + observe API (`Wurk::API`).** A bearer-token-scoped `/v1` JSON API — enqueue, bulk-enqueue, delete, and inspect queues/jobs/swarm topology — RFC-9457 `problem+json` errors, `Idempotency-Key` support, optional read-only mode and per-token rate limiting. Lazily required, so an app that never calls `config.api_token` pays no boot-time cost. Ships standalone (`mount Wurk::API`), engine-nested (`<mount>/api/v1`), or via `wurk api`; a thin Python reference client lives in `clients/python/`. [`docs/api-http.md`](../api-http.md). (#403, #406, #407)
- **OpenTelemetry tracing (`Wurk::Telemetry`).** Opt-in `config.telemetry = true` (requires the optional `opentelemetry-api` gem, never a runtime dependency). Client middleware injects W3C `traceparent`/`tracestate` as top-level job-JSON strings on push; server middleware opens one span per attempt in the OTel messaging vocabulary, parenting to the enqueue span within 60s and falling back to a span *link* beyond that so a job stuck for hours doesn't stretch one trace across it. Retries reuse the original `traceparent`. `Job::Interrupted`/`JobRetry::Handled` (incl. `Skip`, `Limiter::Rescheduled`) record as non-errors; everything else records as an error span. (#403)
- **Flows — DAGs on batches (`Wurk::Flow`).** Each flow node is one job wrapped in its own `Wurk::Batch`; `depends_on:` names build a dependency graph (cycle/`MAX_NODES`(1,000)/`MAX_DEPTH`(50)/`MAX_WIDTH`(100) validated before any Redis write, atomically created in one Lua script), and `pipe:` splices an upstream node's `Wurk::Status` result into a downstream node's args without a JSON round trip. `Flow.abandon(fid)` is a kill switch. No `Sidekiq::Flow` upstream surface exists — checked against the pinned parity SHA and RubyGems before aliasing `Sidekiq::Flow = Wurk::Flow`. [`docs/flows.md`](../flows.md). (#411)
- **Per-job timeouts & deadlines (`timeout:` / `deadline:`).** `timeout:` bounds a single attempt (raises `Wurk::Job::TimedOut`, retried on the class's own policy); `deadline:` bounds the job as a whole from enqueue (raises `Wurk::Job::DeadlineExceeded`, books `stat:expired`/`jobs.expired`, never retried). Both are enforced by `Wurk::Watchdog`, one lazily-spawned monotonic timer thread per capsule — measured at 3.0µs/bounded job versus 4.5µs for stdlib `Timeout` and 27.4µs for thread-per-job. Unbounded classes cost one Hash lookup. [`docs/retries.md`](../retries.md). (#404)
- **Debounce, throttle-to-slot & collapse (`collapse:`).** `sidekiq_options collapse: { policy: :debounce, wait:, max_wait: }` coalesces a burst of pushes into one job — the *last* payload, fired once the burst goes quiet, in one atomic Lua script. `collapse: { policy: :throttle, slot: }` admits the *first* push per fixed, epoch-aligned time slot and drops the rest. Named `collapse:` rather than the plan's original `unique:` after checking that `sidekiq-unique-jobs` already maps `unique:` to its own `lock:` option — reusing it would silently break a host's existing declaration. Conflicts with `unique_for:`/`unique_until:` are rejected at both class-definition time and push time; `push_bulk` rejects a batch outright rather than deciding per item (measured: 1,000 jobs = 2 commands/1 round trip rejected, vs 6,000 commands/1,000 round trips per-item). [`docs/unique-jobs.md`](../unique-jobs.md). (#405)
- **Global per-queue concurrency caps (`config.global_concurrency`).** `config.global_concurrency = { "critical" => 20 }` caps in-flight jobs for a queue across the whole cluster — a Lua-scripted slot claim folded into the existing fetch pipeline (no added round trip when capped), released on every exit path including a `SIGKILL`'d slot holder (TTL-recovered), refreshed on the existing heartbeat pipeline. A capped-and-full queue is skipped locally with a short backoff so other queues stay fair; unconfigured stays at the same 3.00 commands/job baseline. Distinct from the per-key `Wurk::Limiter`s — see [`docs/rate-limiting.md`](../rate-limiting.md) for which to reach for. (#410)
- **Dashboard theme, locale & timezone.** Light/dark/system theme (`config.web.default_theme`, live `prefers-color-scheme` listener, pre-paint stamp to avoid a flash of the wrong theme); a server-negotiated `#wurk-root[data-locale]` hint mirroring the SPA's exact/language-only/default match algorithm across 8 locales; a filterable ~400-zone timezone picker (`wurk.tz` override) applied to every relative and absolute timestamp in the SPA, with a shared live-tick timer so relative labels stay current with no per-cell polling.

### Changed

- **Docs now credit Sidekiq rather than position against it.** The README, [`docs/migrate-from-sidekiq.md`](../migrate-from-sidekiq.md), [`docs/compatibility.md`](../compatibility.md), the site and `llms.txt` framed Sidekiq's tiers mainly as something to be freed from ("what you'd otherwise pay for", "no per-seat math"). That undersold a decade of work the whole ecosystem is built on: Sidekiq's API is the one Wurk implements, and the Pro/Enterprise model is what funded keeping it stable and documented long enough to be worth reimplementing. A new **Why Wurk exists** section (README, and an `#why` section on the site) states the actual difference — Wurk is maintained AI-first, which is what makes a free Pro + Enterprise surface, mechanically-verified parity on every push, and this feature cadence sustainable — and says plainly that Sidekiq Pro/Enterprise remain the better choice for teams who need a commercial support contract. `llms.txt` carries the same instruction so agents summarising Wurk don't manufacture a rivalry. No behavior or API change.
- **Job JSON gains new top-level, additive-only fields — never sent unless the corresponding feature is opted into.** `traceparent`/`tracestate` (telemetry), a `status:<jid>` side-record keyed off `track: true` (no job-JSON field, a separate Redis key), `timeout`/`deadline`/`deadline_at` (per-job bounds — `deadline:` is the input option and is kept verbatim; `deadline_at` is the absolute cutoff derived from it once, at push), `collapse` (debounce/throttle policy). Precedent for additive top-level keys: `job_util.rb`'s existing `TRANSIENT_ATTRIBUTES`, plus `sidekiq-cron`/`sidekiq-unique-jobs` both adding their own. None of these are read by, or break, an unmodified Sidekiq worker.

### Fixed

- **An interrupted `IterableJob` run no longer books as a failure.** `Metrics::History#call` and `Metrics::Statsd#call` now rescue `Wurk::Job::Interrupted` and re-raise it unmodified, so the exception propagates up through them to `InterruptHandler` without flipping the `success` flag. Both metrics middlewares now book an interrupted run as `jobs.success` + duration, never `jobs.failure` — matching upstream's own `Sidekiq::Metrics::ExecutionTracker` treatment of `JobRetry::Skip`. A resumed run that later completes books a second success and duration on top of the first, intentionally, as the job re-enters the middleware chain. Chain order verified in regression tests. (#394)
