# 1.7.0 — 2026-08-10

A maintenance release with three unrelated threads: the Ruby that runs between `conn.call(...)` and the socket got cheaper, CI stopped running the same suite four times, and the docs stopped writing about Sidekiq at length. No Redis key, command sequence, job-JSON field, or public API changed — a 1.6.0 worker and a 1.7.0 worker can drain the same queue.

### Added

- **`Wurk::CommandBuilder` — an allocation-free fast path for Redis command normalization.** redis-client's default builder splices Hash arguments with a `flat_map` and stringifies the result with a `map!`: two array allocations and two per-element type dispatches for a command whose arguments are already Strings, which is what all three commands per job are (`LMOVE`, `LREM`, `DEL`) and both on the enqueue path (`SADD`, `LPUSH`). The fast path short-circuits that case; a Hash to splice, a Symbol or number to stringify, keyword arguments, or an empty command all fall straight through to redis-client's own builder, so the semantics keep exactly one implementation. Installed as the pool default, and a host-supplied `command_builder:` still wins. Measured **~2.1µs → ~0.48µs per command** (`bin/rake bench:command_builder`, now in the regression gate); the frame disappears from the fetch+execute CPU profile entirely, where it was 4.4%, and the `flat_map` it drove falls from 4.3% to 2.1%.
- **`Wurk::PidCache` — `Process.pid` memoized across forks.** glibc dropped its `getpid` cache in 2.25, so `Process.pid` is a real syscall (~640ns measured), and the hot path called it twice per job: `Component.tid` and `Fetcher::Reliable#queue_keys`, both of which read it *only* to notice a fork. The memo refreshes in the child half of every fork through the `Process._fork` hook (prepended, so it composes with other gems' hooks), which is the only event that can change the answer. The frame was 1.0% of the fetch+execute CPU profile and is now absent from it.
- **`bin/profile` — sample a hot path against a real Redis.** `bin/profile` (fetch+execute), `bin/profile enqueue`, `--alloc` for allocation counts, `--dump` to keep the raw StackProf dump. `rake bench` says *that* something regressed; this says *where*. stackprof is a development-group dependency, never a gemspec one.
- **`bin/check` — the pre-PR gate in one command.** `bin/check fast` (rubocop + unit), `bin/check` (+ full suite + parity), `bin/check full` (+ ecosystem). Refuses to start without a local Redis and says how to get one; prints a per-stage wall clock so the slow stage is obvious.

### Changed

- **`require "wurk"` is ~35% cheaper: ~290ms → ~186ms.** Three subtrees pulled heavy stdlib into every boot for code most processes never reach. `Wurk::CLI` required `optparse`, `yaml` and `erb` at load (~45ms) for a command-line parser only `exe/wurk` runs; `Wurk::Profiler` required `tempfile` (which drags in `tmpdir`, ~19ms) for a path that needs vernier loaded *and* profiling switched on for a job; and `Wurk::Web::Extension` required `erb` and `cgi` (~40ms) although nothing reaches them until a host has registered a Web extension and a request arrives. Each now requires inside the one method that uses it — `require` is idempotent, so every call after the first is a `$LOADED_FEATURES` lookup. What is left is dominated by `openssl`, which redis-client's own config pulls in and Wurk cannot avoid. This is boot time for every worker, every fork in a swarm, and every Rails app that loads the gem.
- **Docs no longer name individuals, and say much less about Sidekiq.** The README's *On Sidekiq* note, *Why Wurk exists*, `docs/compatibility.md`, `docs/migrate-from-sidekiq.md`, the site and `llms.txt` all carried multi-paragraph appreciations of Sidekiq's history and its maintainers by name. That is now one line of substance in each place: Sidekiq is human-maintained and funds that through its paid tiers, Wurk is AI-maintained, and that is what lets the same surface be free software. The independence/non-affiliation disclaimer and the trademark attribution stay — they are the parts that carry legal weight. `llms.txt` instructs agents not to name individual maintainers of either project.
- **The README states what Wurk is for.** It is in production at developerz.ai and partner deployments — millions of jobs an hour across many servers — and it is aimed at large fleets in particular: Kubernetes `/live`+`/ready` probes from a config line, a bearer-scoped HTTP API for non-Ruby producers, OpenTelemetry propagation, cluster-wide per-queue concurrency caps, and monitoring built into the dashboard you already mount rather than a separate stack.
- **CI runs one Ruby suite per PR instead of four.** It was a three-leg version matrix (3.3/8.0, 3.4/7.2, 4.0/8.0) plus a separate `coverage` job running the identical suite a second time under SimpleCov — four executions to answer two questions, on Rails lines that were no longer the newest. Now: one job, newest Ruby (4.0) × newest Rails (8.1), with `COVERAGE=1` on the same invocation so the test gate and the line+branch coverage gate share a run. The gemspec's `>= 3.2` floor is held by rubocop's `TargetRubyVersion: 3.2`, which rejects syntax and APIs newer than it. Parity and bench moved to the same pins so they share one gem cache. The ecosystem, pages and release jobs deliberately stay a Ruby behind: ecosystem's subject is third-party gems at pinned upstream SHAs, and Ruby 4.0 dropped `benchmark` from the default gems that sidekiq-cron's own suite requires; pages and release make no compatibility statement, so a newer interpreter there is risk without upside.
- **The parallel test-worker count is now documented rather than incidental.** It stays at 4, and `test_helper` says why: the suite reads like a pure fan-out of independent classes, but its integration layer boots real swarms (4 children × 5 threads each) and carries real socket timeouts, so one worker per core oversubscribes and fails on wall clock instead of on assertions — measured at ~20% wall clock for a red build on a 12-core box. `NCPU` is the knob for a machine with headroom; `NCPU=1` chases ordering flakes.
- **`JobLogger` reads `logged_job_attributes` once**, in its constructor, instead of walking the capsule's delegating `config[]` per job for a list that is fixed the moment the configuration freezes (1.4% → 1.0% of the profile). Altogether the three changes above take about 6% out of a CPU path where roughly a quarter is socket syscalls, and move `bench/memory.rb`'s allocation gate — which is deterministic, unlike the throughput benches — from 6.49 to 6.76 jobs per 1,000 allocations (~4% fewer allocations per job).
- **Redis service containers in CI probe every 2s instead of every 5s**, and `rubocop` runs `--parallel` behind a result cache.

### Fixed

- **`CsrfSameOriginTest` no longer flakes on a stolen fixture.** It seeded the global `retry`/`schedule` zsets at `Time.now` — immediately due — and those keys are un-namespaced by wire-compat, so any poller or `/wurk/api/<set>/all/<cmd>` drain running in a sibling suite on the same worker's Redis DB could promote or delete the entry between `setup` and the request, which then 404'd. Fixtures are now scored an hour out (invisible to every poller, and the route key is just `<score>|<jid>`), and the class opts out of `parallelize_me!` for the same reason `ApiMutationsTest` already does — non-parallel tests run serially in the runner thread, so the two suites can no longer interleave.
- **The 10k-job global-concurrency drain test scales its budget with the worker count.** Its 120s wall clock was a hang detector calibrated at 4 parallel workers; at a higher worker count the same 4-child swarm gets a smaller share of the machine and the test failed on throughput rather than on the leak it actually asserts.
